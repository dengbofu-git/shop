# 完整虚拟茶商品数据

日期：2026-10-16（Asia/Shanghai）。商品模块版本：`goods 0.2.0`。

## 数据范围

批次 `VTEA-20261016` 生成 100 种不同的虚拟茶商品：100 个独立 SPU，每个 SPU 配一个 SKU。基本分类分布为绿茶 20、红茶 20、乌龙茶 20、白茶 15、黄茶 10、黑茶 15，不将 100 个产品误建成 100 个基本茶类。

每款名称带 `【虚拟】` 标记，副标题带虚拟测试批次，所有产地、口感、香气、工艺建议和用途为演示数据，不代表真实商品或检测认证。所有新商品上架以供本地商城与推荐流程使用。

- 复用现有红茶和绿茶分类，补齐其余四个分类；每类创建一个虚拟品牌及商品属性模板。
- SPU 补齐品牌、类别、现有店家、销售及评论计数；SKU 补齐副标题、USD 单价/成本价/市场价、库存、推荐标志、上架状态、版本及时间戳。
- 每款创建净含量、包装、等级三维销售属性与 SKU 多对多关联，并创建对应 SPU 规格和 SKU 规格值。
- 每个类别模板含 25 项属性：虚拟批次、虚拟标志、模拟国家/地区、净含量、包装、形态、等级、配料、口感、香气、场景、采摘季节、生产日期、保质期、冲泡水温/时长、储存、币种、每100克单价、器具、追溯、焙火、批号、最小采购量。
- 属性值按 text/select/multiselect、number、boolean、date 存入相应类型列；不适用的其他值列保留 NULL，不填伪造的数值或日期。
- 图片与品牌 Logo 留空，不创建没有图片文件的 SKUImage 空记录。销量、评价从 0 开始，不伪造交易记录。
- 每款建立初始库存和入库日志，预留数量为 0，SKU stock 与台账 available_quantity 一致；仓库信息全部是明显的虚拟占位信息。

## 写入与备份

管理命令先确认 `default` 为原业务 MySQL，数据库名与显式参数 `--expected-database-name` 一致，服务器 UUID 与参数一致，并检查指定店家有效。原有商品和库存表数据在写入前保存到 `*-before.json`。

同一事务创建所有商品及关联数据，逐条执行模型字段校验，检查最终商品和属性数量及库存一致性；失败则回滚新增数据。批次重复执行时识别已存在的 100 个商品并退出，不重复追加。

本批使用现有店家 ID 8（与现存商品相同），不创建或修改用户账号。

```powershell
python manage.py seed_virtual_tea_products --merchant-id 8 --expected-database-name <实际数据库名> --expected-server-uuid 6b35ae3b-0afa-11f1-808b-2632d3201c4a --batch VTEA-20261016 --as-of 2026-10-16 --report-dir reports/virtual-products/2026-10-16
```

此命令会写入数据。更换批次会追加另一批商品，执行前应确认用途。

## 导出文件

目录：[本次虚拟商品数据](../reports/virtual-products/2026-10-16/)。

- `catalog.md`：100 款名称、分类、SKU ID、规格、USD 单价、库存及模拟使用场景。
- `VTEA-20261016-plan.json`：生成规则对应的完整业务属性。
- `VTEA-20261016-before.json`：写入前相关表原数据。
- `VTEA-20261016-fixture.json`：完整模型字段、主外键、时间戳、类型属性、规格和库存记录；引用店家账号须预先存在，不导出账号凭据。
- `VTEA-20261016-manifest.json`：实际创建的模型数量、ID、分类分布和商品清单，便于定位本批数据。

旧 Agent 对照评测使用的是生成前商品快照，该历史报告保留原语境；新增 100 个商品后推荐候选已改变，不能直接复用旧报告的推荐结果作为当前结果。
