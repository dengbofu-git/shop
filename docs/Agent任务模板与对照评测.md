# Agent 任务模板与对照评测

实现版本：`support_ai 0.6.0`，前端标签 `web 0.4.1`。日期：2026-10-16（Asia/Shanghai）。

## 运行机制

`workflow.py` 执行：脱敏 → 必要的追问解析 → 有限意图提取 → 程序生成模板 → 校验依赖 → 顺序执行白名单工具 → 有序汇总 → 合规检查 → 响应。

- `planning.py`：有限任务类型为 recommendation、question_answering、product_details、after_sales、clarification。明确本轮动词与否定优先使用规则，历史只补充省略表达；其余表达调用模型提取有限类型和本轮原文引用，不允许模型生成工具名或执行依赖。
- 模板固定映射到 recommend_products、introduce_tea、get_product_details、get_order_status、ask_clarification。同种任务合并，单次最多 5 步；用户展示顺序与依赖执行顺序分别保存。
- 推荐后介绍该商品时，商品详情依赖推荐结果。执行器解析真实结果引用，不接受模型编造商品 ID。数据依赖优先执行，最终按用户任务顺序组织回复。
- `execution.py`：检查工具与意图映射、步骤身份、引用类型、未知依赖及环路。工具只能返回结果，不能增加任务或决定下一工具。前置 no_match/error/needs_clarification 会跳过依赖步骤，独立任务继续执行。
- 时间预算为工具间派发预算，默认 90 秒，并不是可强制中断在途调用的总请求硬超时；模型及重排序在途调用仍受各自客户端超时限制。
- `tool_services.py`：由已认证请求创建工具闭包。用户身份、订单状态及检索权限来自应用，不接受模型指定。简单品类、范围词及已验证偏好用程序槽位；复杂购买约束使用结构化模型提取后验证原文证据。

## 商品与上下文边界

- “茶叶/商品”等为范围词，不能直接成为不存在的分类。若宽泛推荐与本轮介绍只涉及一种明确茶类，可使用该共同主题；分别指定不同购买与介绍主题时以购买子任务为准。
- 当前或历史出现预算、币种、品牌、排除条件时，不使用简单槽位快速路径，继续提取并验证条件。未知具体分类先澄清，不静默丢弃。
- 推荐数量限制 1—4，单一结果才能直接用于没有位置说明的“这款”；多候选需明确位置或名称。商品详情每次重新检查可售状态及库存，历史名称仅供识别对象。
- 长期偏好只用于软条件。服务器验证偏好 ID 及值属于当前用户后规范引用，不把模型添加的字段名前缀当原文，也不放松硬条件的证据要求。
- “日常饮用”等用途没有商品属性证据时明确标记尚未验证。当前销量及 ID 后备排序未改为个性化用途排序。
- 会话仍使用 24 小时内最多 6 轮、6000 字符历史；售后引用每轮重新校验归属、查询最新状态。

## 响应与监控

保留 answer、recommendations、knowledge_sources、memory_used 等字段，增加：

- `intents`：有序任务类型；多任务主标签为 `multi_intent`。
- `task_plan`：固定模板计划、依赖、输出顺序和来源。
- `tasks`：各步骤的工具及状态；`unmet_requirements` 为当前无法验证或满足的要求。
- `intent_source`：rules/context_rule/model/clarification。`confidence` 为 null，不把规则匹配当作概率。

单一推荐和澄清使用应用模板生成文本；涉及知识、商品详情、售后或多任务时再统一汇总并检查合规。全部工具失败返回 503，不提交对话；部分任务失败会明确说明，保留独立成功结果。

OTel 增加计划来源、步骤数、意图列表、工具状态、成功/失败任务计数，仍不记录问题、回答、历史、真实订单号或用户身份。规则明确时可以零模型调用，但数据库和工具执行仍有链路。
