# Agent 多轮对话及后续优化方案

更新日期：2026-10-16（Asia/Shanghai）；实现版本：`support_ai 0.5.0`。

后续版本说明：本文保留 0.5.0 的实现与当时待办语境。当前 0.6.0 已使用有限意图、固定任务模板和受控执行器，并完成授权的历史回放；新增能力及评测见 [Agent 任务模板与对照评测](Agent任务模板与对照评测.md)。下方“未运行测试”及“待实施”仅描述 0.5.0 当时状态。

## 已实现：各分支使用同会话历史

每次请求先验证用户和会话归属，读取已成功提交的脱敏历史，再执行以下流程：

1. 对本轮输入及历史文字脱敏。
2. 有历史时调用指代解析模型，将省略或追问补全为独立问题；明确的新问题保留原意。模型必须引用现有历史 turn_id，改写却未引用历史或引用不存在的轮次时降级。
3. 分类器同时接收本轮原话、解析结果及历史。解析结果辅助理解，不覆盖用户原话。
4. 指代无法唯一确定时进入澄清分支；其他请求进入原有意图分支。
5. 商品推荐接收原话、解析及历史、长期偏好；知识问答和售后接收原话、解析及历史；低置信度分支结合历史澄清。
6. 文本回复的总结和合规节点也接收同一份历史。商品推荐仍由应用校验结构化条件、查询实时商品并构造回复。

知识问答的向量化与重排序使用同一个补全问题。例如“介绍绿茶”后的“它怎么泡”，可以解析为“绿茶怎么冲泡”，再据此检索。无充分知识证据时仍需说明缺失，不允许从历史助手回答中补造事实。

解析失败时不让整次请求因可选改写失败而终止，保留原问题与历史继续处理；此时检索可能无法充分消除指代，需结合证据进行澄清。新增模型节点会增加有历史请求的模型调用次数及耗时。

## 历史范围与商品指代

- 最近 24 小时、最多 6 轮问答；不是读取全部历史给模型。
- 每轮助手文字最多 1500 字符；历史预算 6000 字符，包含 JSON 元数据和商品名称引用。优先保留较近轮次，按时间正序传入。
- 历史商品列表额外保留最多 4 个名称和原始位置，帮助理解“第二款”等指代。历史回答中的价格、库存不是当前事实，额外的商品引用结构不携带价格库存。
- 商品推荐的硬条件仍须有当前或历史用户原话依据，助手商品列表只辅助消歧。若只能由助手列表确定购买对象而缺乏用户名称证据，需要确认名称，不得伪造证据。自动将列表指代绑定到经服务端校验的 SKU 属于后续优化。
- 新对话不加载旧会话历史或订单引用；账号级手动长期偏好保持原有行为。
- 页面恢复仍显示该会话最近 6 轮，不等于模型使用的最近 24 小时上下文；历史列表分页和过期提示未在本次实现。

## 售后订单连续性

`SupportConversation.active_order_id` 与 `active_order_at` 仅供服务端使用，真实订单号不进入模型、响应或监控属性。

- 本轮明确提供本人订单号时选择该订单；成功提交售后轮次时记住引用。
- 后续省略订单号时，可在 24 小时有效期内沿用当前会话所选订单；每轮重新检查归属并读取最新状态，不沿用旧回复中的状态。
- 提供未知订单号时不回退到已选订单；要求近期、其他或全部订单时重置本轮选择，使用最多 3 条近期订单的必要状态。
- 多个近期订单没有唯一指代时由售后节点要求明确对象。当前不支持仅按上轮近期订单列表的“第二个”自动绑定订单。
- 旧会话在迁移后没有预设订单引用，需要用户再次明确选择。

部署时在原 MySQL 执行增量迁移：`python manage.py migrate support_ai --database default`。迁移仅增加字段，不删除原会话和问答。

## 监控

新增 `dialogue.resolve` Span，白名单属性为历史轮数 `agent.context.turns`、序列化字符数 `agent.context.chars`、解析状态 `agent.context.resolution`（empty/resolved/fallback）、澄清标记 `agent.context.clarification`。沿用现有运营页面的链路明细查看，不记录原问题、改写正文、历史正文或订单号。

本版本未新增或运行自动化测试，未发起真实模型问答回放；部署检查不代表意图及推荐质量验收通过。

## 待实施：针对 2026-10-15 晚间记录的优化方案

以下为方案，未作为本次多轮接入一并实现。

### P0：意图与任务规划

- 将单一最高分路由改为结构化任务计划，输出主意图、辅助任务、是否话题切换、是否回复待澄清问题及判断依据。
- 对本轮“介绍/比较/解释”等明确知识请求优先识别；只有省略表达才沿用会话意图。历史助手路由和回复不能反过来充当本轮购买意愿证据。
- “推荐茶叶，介绍绿茶”拆为知识介绍与商品查询两个任务，分别取证后合成回复。
- 低置信度按问题相关性和缺失信息进行澄清；不因低分推断功能未开发。多轮接入已提供上下文澄清基础，尚未重构分类分数、阈值及组合任务执行。
- 验收重点：连续推荐之后的“介绍绿茶”“介绍一下中东的茶叶详情”“介绍一下各种茶叶”正确进入知识任务；新会话“介绍茶叶”获得知识回答或范围澄清。

### P0：分类映射与宽泛推荐

- 在应用层提供有效分类词表及受控别名。原文条件、规范化分类 ID 和映射依据分别保留，不让模型直接决定数据库身份。
- “茶叶/茶/商品”作为商城范围词，不生成不存在的必须分类；“红茶/绿茶”等映射到有效分类。
- 未识别分类与真实过滤后无商品分开处理；允许提出候选分类让用户确认，不能静默丢弃明确条件。
- 宽泛推荐默认搜索当前可售商品，长期偏好只影响排序；品类、品牌、预算均非必填。只对互相冲突或确实无法执行的条件澄清。
- 验收重点：同一句“推荐茶叶”不因提取出不存在分类而空结果；“推荐商品”可以先返回候选。

### P1：推荐约束、商品属性及排序

- 提取推荐数量、用途、软偏好和硬约束；“推荐一款”最多返回 1 款，未能验证“适合日常饮用”时明确说明依据不足。
- 为商品补充净含量、包装、用途、已证实的风味等结构化属性。价格单位仍以商城实际币种为准，缺失重量时不计算每克价格。
- 排序按已验证属性匹配、软偏好、明确价格偏好等可解释因素组合；销量和 ID 作为后备因素。不能因为用户说“日常”就假设其预算或认定贵的商品不适合。
- 商品标题优先展示 SPU 名称加 SKU 规格，避免只显示“默认规格”。理由说明具体匹配点及未满足项。
- 列表指代后续增加独立的服务端 SKU 引用校验，每次重查上架、库存和价格，再执行比较或筛选。

### P1：质量观测及验收设计

- 记录完整意图分数、分差、任务完成情况、分类映射状态、候选及过滤数量；正文与用户信息继续排除在 OTel 之外。
- 区分技术成功、有效澄清、无商品、语义误判和未完成任务，不能将 HTTP 200 或 Span OK 当作推荐准确。
- 经授权再使用已脱敏的昨晚样例及对照会话进行回放；人工标注意图和应满足约束，分别计算路由正确率、有效推荐率、约束满足率及多轮一致性。小样本不当作全量准确率。
