## 1. 项目定位与当前版本

系统采用 Django 多App单体后端、Django模板和 jQuery／原生JavaScript多页面前端，服务买家采购、茶企经营和平台运营。依赖清单约定Python 3.9，Django固定为3.2.12；AI编排使用LangChain／LangGraph。没有独立Vue／React工程或前端打包步骤。

## 2. 运行与数据边界

| 组件 | 当前用途 | 默认本地地址／来源 |
| --- | --- | --- |
| Django | 页面、业务API、管理后台 | `127.0.0.1:8000`；`manage.py` |
| MySQL，别名`default` | 用户、商品、订单、库存、收藏足迹；客服会话、Agent配置／变更和监控投影 | `.env`中的`DB_*` |
| PostgreSQL＋pgvector，别名`ai_storage` | `BuyerMemory`、知识文档／片段和向量空间 | `127.0.0.1:5433`；`.env.postgres` |
| Redis | 默认缓存DB0、采购车DB1 | 默认`127.0.0.1:6379`；支持`REDIS_CACHE_URL`、`REDIS_CARTS_URL`和`REDIS_PASSWORD` |
| 模型服务 | 买家Agent的OpenAI兼容接口 | `.env`中的`SUPPORT_BASE_URL`、`SUPPORT_API_KEY` |
| Ollama／BGE-M3 | 知识入库及查询Embedding | `127.0.0.1:11434`；`compose.ai-storage.yml` |
| BGE重排序服务 | 按运营配置对知识候选重排序 | `127.0.0.1:18081`；`compose.reranker.yml` |
| OTel／Jaeger／Prometheus | 可选链路导出及指标查看 | OTLP HTTP `4318`、Jaeger `16686`、Prometheus `9091` |

`ai_storage/router.py`将AI存储的读写／迁移限定到PostgreSQL；其他业务留在MySQL。`BuyerMemory.owner_id`对应MySQL用户ID，但不是跨库外键。恢复两库时要保持身份ID对应，不能依赖账号删除自动级联清理PostgreSQL，也没有跨两库原子事务的保证。

`media/`是运行数据的一部分。数据库图片字段保存文件路径，迁移数据库不会迁移图片；交接和部署必须同时交接媒体文件。容器模型缓存、PostgreSQL和Prometheus使用各自持久卷。

| 平台运营 | 统一`login.html`按权限分流至`admin_panel.html`或`admin_agents.html` | 用户管理、模型／重排序设置、配置变更及Agent链路查看 |
| Django Admin | `/admin/` | Django自带管理后台，使用Django认证账号 |
| 商品溯源 | 页面已移除，卡片按钮禁用 | 未接通生产溯源链路 |

页面路由并非严格等于App名；API挂载见根路由。多数商品和交易API不带末尾斜线，客服与商家助手API带末尾斜线，联调时按各App的`urls.py`使用准确路径。

业务端使用`users.UserProfile`、JWT和RBAC，前端由`client/static/js/auth-storage.js`管理Token。登录页仅有一个账号密码入口，服务端按有效角色和权限返回工作台地址；旧终端入口重定向统一登录。平台账号须同时具备有效平台角色与对应的`user_manage`或`system_config`，停用账号／角色／权限不计入授权。平台无可用权限时拒绝进入；商家／供应商和买家分别进入自己的工作台，页面入口不能代替API鉴权。详情见[统一登录规则](sdd/modules/identity/unified-login.md)。

业务运营账号`admin`由业务命令维护；Django Admin账号由`python manage.py createsuperuser`创建，两者不能互相替代。已有环境不要把账号初始化命令当作普通启动步骤。平台现定位为跨境茶叶 SaaS，当前没有租户隔离、订阅套餐或自动计费实现。

## 4. 新机器启动与已有环境接手

以下命令在仓库根目录执行。工作目录以实际克隆位置为准，工程包改名不移动工作区根目录。项目基础环境说明仍见 [环境配置](环境配置.md)，双库和AI部分结合本节及对应专题使用。

### 4.1 Python和配置

```powershell
conda create -n tea_saas python=3.9 -y
conda activate tea_saas
python -m pip install -r requirements.txt
if (-not (Test-Path -LiteralPath .env)) { Copy-Item -LiteralPath .env.example -Destination .env }
if (-not (Test-Path -LiteralPath .env.postgres)) { Copy-Item -LiteralPath .env.postgres.example -Destination .env.postgres }
```

已存在的配置不要覆盖。创建MySQL业务库，按`.env.example`补齐密钥、`DB_*`及相关服务变量；用AI能力时再填写PostgreSQL凭据和模型服务。示例中的空值只是占位，不代表外部服务可用。

- 加载顺序为进程环境→`.env`→`.env.postgres`，后两者不覆盖已存在的值。跨文件重复键应清理，避免实际值与预期不一致。
- 多个环境变量在导入`settings.py`时通过`os.environ[...]`读取；未启用支付／AI时也需要保留示例中的键，真正调用对应能力时才要求有效服务配置。
- 短信验证码、邮箱激活／找回密码及微博认证接口已移除；注册与登录使用账号密码，邮箱和手机号仅作为账号资料。旧认证服务配置不再参与启动。
- Redis地址和认证通过`.env`的`REDIS_CACHE_URL`、`REDIS_CARTS_URL`、`REDIS_PASSWORD`配置，详情见[环境配置](环境配置.md#4-redis)。配置变更后重启Django。
- `.env`、`.env.postgres`、API Key和应用私钥不进Git或交接文档；仓库中只维护示例变量名和公钥。

### 4.2 业务数据库与基础启动

先启动MySQL、Redis。新库先在MySQL中创建数据库；已有库先确认连接目标、备份和待执行计划，再应用迁移。

```powershell
python manage.py check
python manage.py migrate --plan --database default
python manage.py migrate --database default
```

仅在新环境初始化或明确需要重建权限／账号时执行：

```powershell
python manage.py seed_rbac
python manage.py create_super_admin
```

`create_super_admin`会把已有`admin`密码重置为`ADMIN_INITIAL_PASSWORD`并激活账号，日常启动不要重复执行。完成初始化后：

```powershell
python manage.py runserver 127.0.0.1:8000
```

打开 [登录页](http://127.0.0.1:8000/login.html)。通过Django路由访问模板，不直接从磁盘打开HTML。

当前`client/static/js/init.js`的`baseUrl`、`frontendBaseUrl`和`imgUrl`，以及`settings.TEA_SAAS_MEDIA`仍使用`127.0.0.1:8000`。更换访问域名／端口或拆分前后端时，要同步检查这些值、`ALLOWED_HOSTS`、CORS与回调配置；只改runserver端口不会自动修正全部资源和跳转。

### 4.3 AI知识存储与重排序

MySQL迁移不会替你迁移PostgreSQL。启用知识问答前执行：

```powershell
docker compose --env-file .env.postgres -f compose.ai-storage.yml up -d --wait
docker compose --env-file .env.postgres -f compose.ai-storage.yml exec ollama ollama pull bge-m3
python manage.py migrate ai_storage --database ai_storage
```

新环境需要示例知识语料时，再运行`python manage.py import_middle_east_tea_knowledge`。该命令调用本地Embedding并写入PostgreSQL；重跑会更新既有来源文档并重建其片段，不能当作只读健康检查。

需要启用重排序时：

```powershell
docker compose --env-file deploy/reranker/compose.env.example -f compose.reranker.yml up -d --build
```

确认服务加载完成，再在`admin_agents.html`启用和设置参数。当前完整业务迁移已包含`support_ai`至0004，**不要为了重排序单独执行迁移到0003而把已有库退回旧状态**。详细步骤见 [AI存储](PostgreSQL与pgvector配置.md)、[本地重排序](本地重排序.md)。

监控导出是单独能力：`docker compose -f compose.agent-observability.yml up -d`；还需Agent运营配置启用导出。仅启动容器不等于已有Trace。普通停止使用`stop`保留数据卷。

### 7.2 调试买家Agent

```powershell
python -X utf8 -u manage.py agent_preview
# 需要本人订单／私有知识时，明确绑定开发环境中的活跃买家
python -X utf8 -u manage.py agent_preview --user-id <买家ID>
```

该工具直接调用当前真实模型和业务读取服务，不经过网页身份、HTTP限流和持久会话路径；无需启动网页或Redis，但仍依赖所选工具使用的MySQL、PostgreSQL及模型服务。默认独立临时会话，日志位于`reports/agent-preview/`，不写客户会话或偏好。用`/config`、`/plan`、`/rag`核对配置、计划和实际检索，旧终端需退出重启才能加载新代码。详情见[终端预览](Agent终端预览.md)。

## 8. 已知差异与接手优先级

以下是当前源码或记录中已有的具体问题，不因某一模块存在代码、页面可打开或单次测试通过而自动解除。

| 范围 | 接手时必须明确的现状 |
| --- | --- |
| 支付回调 | 当前`pays/views.py::notify`按GET订单号直接更新状态，未见回调验签、金额／币种和幂等校验；真实支付接入前需先补契约与验证 |
| 账号与权限 | 业务密码目前使用MD5；CSRF中间件在配置中注释；JWT、角色装饰器与URL用户名校验并存，不能用前端隐藏入口替代对象权限检查 |
| 库存口径 | 商品详情／采购车取SKU库存和账本可用量较大值；AI推荐在有账本时取账本、无账本时取SKU，尚未统一 |
| 价格币种 | SKU价格字段未独立保存币种；采购页／AI按USD使用，工作台按CNY换算，详情／收藏显示人民币标签。联调报价与支付前需明确统一口径，不能直接把页面标签当成数据库币种事实 |
| 经营展示 | `supplier/analytics.py`部分地区、库存周期等为哈希／推算值；订单完成率与销售趋势来自订单聚合，商家结算展示不等于资金清结算 |
| Agent 0.10.0 | 历史实测15组41轮中37轮满足预设检查、11组全程通过；其余涉及列表序号丢失、条件被拆成澄清、分组理由重复命中详情，仍待修复 |
| RAG | 0.9.0双臂评测未显示整体收益，存在重排／选证据退化；0.10.0的推荐修复未解决该问题，服务ready也不是知识正确率结论 |
| SDD准入 | `CAP-AI-003`仍在SPEC_REVIEW；收藏足迹`CAP-CAT-004`规格0.1.1、阶段IMPLEMENTING。其他候选项及旧对账范围按各自日期阅读，没有全站自动准入检查器 |

完整证据与差异见[实现对账](sdd/reconciliation.md)、[推荐追问测试报告](../reports/agent-evaluation/2026-10-16-dialogue-followups/live-run-1/report.md)和[RAG对照报告](../reports/agent-evaluation/2026-10-16-rag-rewrite/paired-run-1/report.md)。这些是限定样本结果，不作为整体用户准确率或生产验收结论。

排错顺序：先看请求URL／HTTP状态和浏览器Console，再看当前进程版本、配置及对应服务。收藏页加载异常先检查是否还缓存旧JS；图片不显示先检查`goods/images.py`选中的路径及文件是否存在；AI失败分别定位MySQL配置表、PostgreSQL、Embedding、重排序和模型服务，不把所有503都当成模型故障。
