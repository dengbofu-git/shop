# 本地知识重排序

## 组成

知识问答使用：脱敏问题 → BGE-M3 向量 → 已发布和用户权限过滤 → pgvector 候选
→ 正文去重 → BGE Cross Encoder 重排序 → 来源多样性和正文预算 → DeepSeek。
商品、库存、价格和订单仍由业务接口提供。重排序不修改知识文档、向量和商品数据。

模型为 `BAAI/bge-reranker-v2-m3`，固定版本
`953dc6f6f85a1b2dbfca4c34a2796e7dde08d41e`。模型和 tokenizer
均禁止远程代码，使用 safetensors 权重。

## 启动

```powershell
docker compose --env-file deploy/reranker/compose.env.example -f compose.reranker.yml up -d --build
python manage.py migrate support_ai 0003_agent_reranking
```

若本机 Docker Hub 镜像源不可用，可在运行 compose 前设置：

```powershell
$env:RERANK_PYTHON_IMAGE='public.ecr.aws/docker/library/python:3.11-slim-bookworm'
```

compose 显式指定独立环境文件，避免将 Django `.env` 中的密钥当作 compose 变量。
服务仅绑定 `127.0.0.1:18081`；Django 的 `AI_RERANK_BASE_URL` 为服务器设置，
不允许通过运营页面输入任意服务地址。首次启动下载模型，缓存保存在
`tea_saas-reranker_reranker_models` Docker volume；重启会复用缓存。

模型权重约 2.27 GB。网络较慢时可停止重排序服务，将同一模型 volume 挂载到
该镜像，执行 `/app/download_model.py` 并行下载固定版本权重。此工具保留 Hugging Face
已下载前缀，完成后对完整文件核对官方 LFS SHA256；执行期间不能同时启动模型服务。
下载工具失败会恢复原前缀，不能把尚未校验完成的文件当作可用模型。

`GET /health` 返回 `loading`、`ready` 或 `error`，包含模型版本和计算设备。
模型加载和预热完成后才接受推理请求。默认镜像使用 CPU PyTorch，
`AI_RERANK_THREADS` 和 `AI_RERANK_BATCH_SIZE` 控制线程数及批大小。
此 CPU 镜像不能通过单纯添加 GPU 参数启用 CUDA，GPU 部署需另外安装 CUDA 版 PyTorch。

## 运营配置

在 `/admin_agents.html` 的“知识检索与重排序”区域配置：

- 开关和服务器允许的模型。
- 候选数（默认 30，最大 100）、最终证据数（默认 5，最大 20）。
- 每文档片段上限（默认 2），候选不足时放宽。
- 超时时间（默认 5000ms，500–30000ms）。
- 最低相关性分数（默认留空，不过滤）和正文字符预算（默认 12000）。
- 异常回退（默认开启）：超时、忙碌、服务未就绪或无效响应时使用向量排序。
  关闭后，重排序失败不提供知识证据，问答提示词会要求说明证据不足。

默认迁移只增加配置字段，重排序开关初始关闭；服务就绪后在运营页面启用。
保存采用配置版本控制和现有变更审计；同一请求始终使用同一配置快照。
旧客户端提交原有设置字段时保留重排序设置。

当前本机已启用 `30 → 5`，每来源上限 2、阈值留空、字符预算 12000、降级开启。
CPU 首次实际检索“介绍一下绿茶”（含向量化）约 24 秒，5 条结果均有重排序分数，
因此当前运行配置将重排序超时预算调整为 30000ms。该单次结果仅用于部署调优，
不是中英阿业务质量评估，也不代表稳定耗时或性能保证。

每个问题与片段最多 512 tokens，其中问题最多 96 tokens。长片段使用有重叠的
窗口分别评分，取最高分窗口并保留其原文子串。每片段最多 16 个窗口，
每请求最多 256 个窗口；超过限制会进入显式降级，不会静默丢弃尾部内容。
服务只允许单次推理，无排队；忙碌返回 429，避免请求堆积。
客户端和服务端均设截止时间，服务在每批计算之间检查时间。

调用返回的索引必须完整覆盖原候选，分数须为有限的 0–1 数值，窗口文字必须
是对应候选原文的子串；否则整个重排序响应作失败处理。
分数不是事实正确率，不建议未经中英阿业务标注评估就设置统一阈值。
正文预算截断会标记 `context_truncated`。原知识正文保留在 PostgreSQL。

## 监控

链路新增 `knowledge.rerank` 和 `knowledge.select_context`，记录模型版本、候选数、
输入和输出 chunk ID、分数、最终证据 ID；不记录问题和正文。
排名明细仅用于 trace，不作为高基数 metric 标签。

指标为 `agent.rerank.requests`、`agent.rerank.duration`、
`agent.rerank.candidate_count`，按结果和固定原因区分降级。运营页展示调用数、
失败数、降级数、平均耗时和 P95；P95 基于所选时间范围内最近最多 10000 次调用。
无监控记录表示还没有知识问答进入该分支，不代表重排序服务未启动。

知识检索和模型接口的失败不会记录原始异常正文或请求内容。
模型切换目前只列出已部署的 BGE 模型；新增模型时须同步部署服务并更新服务器允许列表，
不能仅在页面填写一个模型名。

## 效果评估与回退

运营启用前后应按相同的中英阿知识问题对比 Recall@30、nDCG@5、引用准确性和
端到端耗时。权限隔离、无资料问题、同来源重复片段及长片段均需纳入评估。
模型质量提升必须以这些结果为依据，不能由服务健康状态推断。
关闭重排序即可恢复向量检索路径，无需删除 volume 或回滚知识库。
