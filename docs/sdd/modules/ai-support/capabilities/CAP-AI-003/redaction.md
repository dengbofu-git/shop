# CAP-AI-003 脱敏与订单引用方案

规格 `0.2.0`／设计 `0.1.0`，状态 `proposed`。依据 REQ-AI-003-01／02／05、RULE-AI-003-01／03／05，覆盖 AC-AI-003-03／07／11。本轮没有修改现有脱敏函数或处理存量数据。

## 当前与目标的区别

[本次对账探针](../../../../evidence/2026-10-16-sdd-reconciliation/manifest.json)重新确认英文编号残留和历史原样返回。下文是目标方案，不是当前脱敏能力清单。

| 目标 | 当前观察 |
| --- | --- |
| 统一编号跨度解析／替换 | 当前查询regex与PII regex不同，且只把本人编号额外传给redact；英文他人／不存在编号可残留 |
| 下划线、超长、多个候选的完整边界处理 | 尚未实现统一规则；当前选择首个本人匹配，不能声称多编号已受控澄清 |
| 临时ctx-1..6引用 | 当前仍为turn-数据库主键 |
| 所有响应文本／历史／重放投影过滤 | 当前主要处理输入与answer；历史GET、成功重放直接返回保存内容 |
| 任意联系方式／凭据过滤 | 当前有有限中文姓名地址、邮箱、中国手机号、数字等模式；不能保证所有国际电话或Token格式 |
| HTTP通用遥测无文本 | 当前有SAFE_ATTRIBUTES白名单与相关测试；CLI预览另会保存现有规则脱敏的输入／输出JSONL，不能推广为全项目无文本日志 |

预览的safe_record虽递归处理字符串，仍复用相同有限redact模式，不能作为英文编号问题已修复或HTTP输出树已覆盖的证据。

## 边界和允许字段

所有身份和权限来自认证应用。模型及其回调只接收经应用构造的输入，不接收 ORM、数据库句柄、请求对象、Authorization、完整用户对象或私有订单引用。

| 数据 | 应用内部 | 模型／工具公开输入 | HTTP和持久化 |
| --- | --- | --- | --- |
| 原始message及编号位置 | 当前请求短暂使用，用于解析和请求指纹 | 替换后才允许进入；识别到的原始编号一律移除 | 不将原文新增到会话／日志；浏览器输入仅留当前页面内存 |
| 当前用户／真实订单号 | 用于本人过滤与最终提交时重查 | 禁止 | active_order_id可在本人私有会话记录保存；不放通用响应／遥测 |
| 订单状态／日期 | 交易域实时读取 | 仅匿名label、status、created_date | 回答可表达该事实；不增加订单详情接口 |
| 历史轮次 | 当前用户、当前会话的已提交轮次 | 再脱敏，最近24小时最多6轮／6000字符 | 恢复接口可以读取更早轮次，必须标历史且在输出投影过滤敏感文本 |
| request_id／conversation_id／revision | 应用幂等和会话控制 | 禁止传入模型提示词 | 可向本人客户端返回；不作为公开订单标签 |
| trace_id、工具状态、计数、异常类 | 运行诊断 | 不是问答输入 | 只用允许的运行字段；不带异常正文、URL查询、原文或原始标识 |
| 长期偏好 | 保留按用户读取；不可用503 | 本订单工具不消费偏好，不注入订单提示词 | 本能力不写；其存储规则归知识域 |

模型可见订单DTO的唯一字段为：

```json
{"order":"当前会话所选订单","status":"待发货","created_date":"2026-10-16"}
```

近期列表使用“近期订单1／2／3”。不加入真实ID、用户、商家、金额、地址、联系方式或未确认的物流事实。DTO采用明确字段映射，拒绝把 `model.__dict__` 或通用序列化结果直接交给模型。

## 解析与替换使用同一套引用结果

当前差异是“查询识别了英文引用，脱敏却没替换”。目标实现只生成一次引用跨度列表，选择订单和文本替换共同消费，避免维护两套语法。

建议本地解析规则（待技术评审）：

1. 带标签：识别 `订单号／订单编号／单号` 与大小写不敏感的 `order id／order number／order #`。允许标签后的空白、`:`、`：` 或 `#`。值按订单字段上限64个字符处理，支持ASCII字母、数字、`-`、`_`；必须匹配完整token，不能截断过长值后查询前缀。
2. 无标签：兼容已有的本人完整编号匹配及10位以上数字候选；边界不能嵌在更长的字母数字或下划线token内部。本人编号匹配来自当前用户范围，不能全表枚举其他用户编号。
3. 标签缺值、值超长／不完整、多编号或无法唯一选择时，本地返回澄清结果；不截断查询、不挑第一个、不回退展示近期本人订单。普通“如何查看订单”没有明确编号，不当作不可查询编号。
4. 无标签的其他字母数字串，仅凭形状无法判定是订单号。出现明确订单查询语境又存在疑似引用且无法归类时，采用本地澄清，不把疑似原文送入模型；普通茶类／商品词不做授权查询。
5. 对一个可解析的明确编号，只在 `user_profile=current_user` 条件下查询。无可见结果统一 `not_queryable`；不再做全局存在性查询。多个候选先澄清，不通过分别报错泄露哪个编号存在。

替换时使用跨度从后向前将**所有**候选编号替换为 `[订单号]`，包括本人、他人、不存在、重复和无效格式的引用。重叠跨度合并；不通过逐次全局字符串替换破坏原文位置。引用提取在一般PII替换之前执行，防止编号被电话／敏感号码规则先破坏。

之后沿用并补齐一般PII过滤：姓名／账号标签、邮箱、手机与国际联系方式、地址、证件／银行卡等敏感号码、Bearer和凭据标签。用途明确的非敏感数字（例如“24小时”）不应因粗暴删数字失去语义。具体模式必须有正反例；不能宣称有限正则能识别任意未标注的自由文本个人信息。

## 三道数据检查

### 输入与历史

本轮问题、本会话历史user_text与assistant_text均再次使用统一替换／一般PII过滤；旧轮次不能因曾保存而免检。调用前扫描所有实际提示词字段，包括消歧、有限意图、汇总和合规检查，不能只检查composer的一段文本。

当前 `turn-<pk>` 用作历史证据引用。目标在发给模型的当前上下文中改成临时 `ctx-1..6`，由应用保留映射；模型返回引用先验证在该上下文集合内，不把临时编号当作新的数据库授权。请求、会话、用户及持久化轮次主键均不作为模型必需字段。

能够证明残留了禁止字段、引用或凭据时，在调用前终止并给安全澄清／不可用反馈，不继续发送原文。无法识别任意自由文本身份是模式方案的已知限制，须用目标语言／合成样本评审和真实实现验证降低遗漏，不能以“已调用redact”当作泄漏检查已通过。

### 模型输出与成功提交

检查完整响应树：`answer`、`task_plan.steps[].request`、诊断、unmet_requirements及其他文本扩展。过滤已知引用和PII，禁止私有字段被增加到JSON。计划仍由程序白名单校验，模型或工具不能追加SQL、身份或交易命令。

合规模型只能辅助；最终应用检查必须在保存和返回前执行。发现不可安全表达的输出时使用现有安全答复语义，不把原始草稿或异常正文保存到SupportTurn；不得为通过检查而改写交易状态。若安全答复按既有合规分支提交200，则明确是无法可靠回答，而非查询成功的订单事实。

### 历史、重放和遥测

历史GET、已提交成功重放也做读取投影过滤，防止旧版本文本重新出现在浏览器或进入下一轮模型。只修改返回投影，不在读取接口批量更新原行；同一存储结果使用确定性投影，除移除敏感信息外不刷新事实或改写业务结果。旧数据清理需Q-013确定。

日志及span使用运行字段白名单，不记录请求体、模型输入输出、原始候选、查询参数、用户／订单／会话标识或完整异常。公开trace_id可用于技术定位，但不携带身份。404不发模型调用、不写成功轮次；允许安全运行计数，不能据此生成虚假成功对话。
