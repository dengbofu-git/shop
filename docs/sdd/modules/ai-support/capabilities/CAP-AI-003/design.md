## 应用读取结果

建议在应用层用显式结果代替 `current_order_context` 的三个位置值，最小包含：

| 字段 | 含义／去向 |
| --- | --- |
| `outcome` | `selected / recent / empty / clarification / not_queryable`，应用控制分支，模型不能设置 |
| `safe_message` | 已替换引用并完成一般脱敏的问题 |
| `orders` | 仅含匿名标签、状态文本、创建日期的DTO，最多三笔 |
| `selected_order_id` | 本人当前选定订单的私有标识，仅用于应用重查和成功提交 |
| `reference_spans` | 请求内的原始引用位置，仅在当前请求内用于替换，禁止进入日志、span、响应和会话 |

数据所有权：`orders.OrderInfo` 及对应试单／预售子记录在业务MySQL，由交易域拥有；本能力只读。`SupportConversation`、`SupportTurn` 在MySQL，属于本能力；`BuyerMemory` 在AI PostgreSQL，只按当前用户读取，本能力不写偏好。

`not_queryable` 表示**一个语法明确的编号在当前用户范围内不可见**，不区分他人或不存在。未指定且本人无订单是 `empty`；多个编号、无法唯一定位或格式不完整是 `clarification`。后两者用应用模板表达，不把无订单解释为故障或让模型补写状态。多编号的具体语法边界见脱敏方案，属于本次待评审细化。

## 新请求执行顺序

1. 保留方法校验、买家Bearer认证、字节／消息／字段校验；计算现有请求指纹。
2. 查当前用户已有成功请求：相同指纹重放200；不同指纹409。该分支不刷新订单状态，不能改成“先查当前订单再重放”。
3. 检查会话归属和初始revision。外人／不存在会话统一404；初始冲突409。
4. 沿用当前历史与偏好读取、模型配置存在性检查。偏好库故障503且不降级，避免以404路径绕过既定依赖失败策略。
5. 在本地提取和脱敏订单引用，按当前用户范围读取订单并返回应用结果。数据库异常503；`not_queryable` 直接返回固定404和 `ORDER_NOT_QUERYABLE`。
6. 对有效订单与普通查询，将脱敏问题、允许的历史和订单DTO交给受控工具图。仅当应用无需模型即可确定是纯订单请求时，`empty / clarification` 可由本地模板完成200；无法本地确定意图或还有其他任务时，确保脱敏后沿用受控编排，订单工具以no_match/needs_clarification表达无事实，不压掉其他合法任务。不能仅因本人无订单就把知识／推荐问题改成订单空结果。
7. 出站检查回答、task_plan、诊断等完整响应，过滤私有字段后才调用 `commit_turn`。最终提交再次检查revision及幂等。
8. 一次成功提交才创建／增加会话轮次、更新选中订单引用并返回标识。任何404、503或最终冲突都不提交成功轮次。监控失败按运行组件边界处理，不能伪造业务结果。

404短路位于模型SDK初始化、模型解析、工具执行和成功提交之前。认证、会话、偏好／配置错误的优先级见API契约；“不调用模型”不表示请求完全没有数据库读取或安全运行事件。

## 会话、幂等与并发

- 新页面保存完整pending请求。网络中断、503后重复同一动作使用相同request_id和原始字段值；改问题或刷新revision后生成新ID。
- 成功记录按 `(user, request_id)` 唯一。保留现有指纹算法，避免把不同原始编号脱敏成同一占位符后误认为同请求。
- 对成功重放只做当前认证与用户隔离，不重新提交、不增加revision。原响应在边界再次脱敏；旧结果标为“重试返回的结果，非实时刷新”。脱敏投影仅在需要移除敏感信息时允许改变旧文本，业务状态不刷新。
- MySQL短事务保留用户行及会话行锁、两个唯一约束，模型调用在事务外。最终冲突返回409，已发生的模型调用不能撤回。
- 404／503不缓存为成功结果。改编号视为新动作；相同404编号重试仍需重新认证和查询，不能把一次不可见结论永久缓存。
- 新追问每轮重读归属和状态；有效选择按现有成功提交记录刷新引用时间。24小时引用窗口和6轮／6000字符模型历史上限继续沿用，原存储保留期不由这些上限推导。
- 当状态在读取后改变时，回复代表本次读取时观察到的事实；不承诺输出瞬间与交易库原子一致。冲突和多种订单状态均不由模型自行修复。

## 错误和前端兼容

保留 `error` 并增加 `error_code`。chat 404区分 `ORDER_NOT_QUERYABLE` 与 `CONVERSATION_NOT_FOUND`；页面不通过中文字符串判断类别。历史读取404只属于会话／路由问题。

新客户端遇到旧服务端无代码的chat 404，按旧服务只有会话404的事实处理；新服务端必须为订单404提供代码。旧客户端可显示新服务端的error文案，但无法完成新错误类型对应的全部交互，所以服务端先上线、前端随后跟进，两者配对后验收。回退旧服务端会失去目标404保证，不能继续声称本规格已实现。

浏览器遇到HTML405、路由404、代理5xx或无效JSON，使用安全通用提示，不显示响应原文。成功响应的原有扩展字段保留，其他能力在同chat入口的字段不由本契约删减。

一个请求含明确不可查询编号及其他任务时，整次新请求404，其他任务不先调用或部分提交。该规则保持当前单请求一次成功提交的事务边界；如将来需要部分成功，另做协议与AC变更。
