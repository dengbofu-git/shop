# 采购页推荐商品：有库存、销量优先

更新：2026-10-19。用户明确要求截图中的“推荐商品”按销量优先展示，本轮修改该区域的数据选择规则。

## 当前规则

- 入口仍为 `GET /v1/goods/recommended-products`，返回字段保持兼容；前端 `buyer-products.js` 继续展示前 6 款，接口最多返回 20 款。
- 候选来自全平台所有已上架 SKU，不再要求 `is_recommended=True`；按 `SKU.sales` 降序、`updated_time` 降序、SKU ID 降序排列。
- 库存过滤在数据库中完成后才取前 20 款，移除旧版先取 80 个候选的限制。高销量但无库存的商品不能挤掉后续有库存商品。
- 沿用该采购接口原有库存口径：`max(SKU.stock, 所有仓库 available_quantity 之和) > 0`。数据库使用两个值任一大于零的等价条件；本轮不统一为 Agent 的“有账本则账本优先”口径，也不改变库存服务。
- 多商家统一竞争销量排名，没有商家配额或轮换；同销量可由更新时间和 ID 决定先后。不对同 SPU 的不同 SKU 合并销量或去重，多个库存仓库不会产生重复 SKU。

## 人工推荐字段

`goods.SKU.is_recommended` 默认 False，Django Admin 的推荐商品管理可人工勾选／取消。虚拟商品种子命令按 `item['index'] % 8 == 0` 标记部分样例；不是销量统计或模型计算结果。

采购页本区域不使用该标记作为入选条件或排序权重。智能客服既有的偏好分、人工推荐标记、销量、ID 排序继续保留，未在本轮修改；后台字段说明同步明确两者差异。没有删除字段、改写迁移或批量修改已有推荐标记。

## 销量数据边界

本次排序直接使用现有 SKU.sales，不根据 SPU.sales、订单条数或订单金额推算，也不补造销量。本轮只读核对时，业务库共有 104 个 SKU，SKU.sales 全部为 0；此时展示先后由更新时间和 ID 决定，不能宣称当前已产生真实热销差异。

在当前订单／支付／库存实现中未找到自动累加该字段的代码。销量维护及支付、取消、退款等统计口径需要后续单独补齐，本次不修改订单事务或回填业务数据。

## 验证

`goods.test_sales_recommendations` 覆盖多商家混排、未标记商品参与、销量优先、下架／无库存排除、超过 80 个无库存候选、同销量稳定排序、双库存源、多仓不重复、最多 20 款和空结果。使用隔离 SQLite，实际 MySQL 只读检查与本地接口结果见[本轮证据](../../evidence/2026-10-19-sales-recommendations/verification.md)。不变更现有能力阶段，不代表已发布。
