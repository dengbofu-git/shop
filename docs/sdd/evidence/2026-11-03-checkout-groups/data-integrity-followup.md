## 实际统计原因

截图唯一匹配本店近365天的107笔订单，全部是普通订单且`currency=NULL`，备份中这些原列也是相同值：

| 订单状态 | 数量 |
| --- | ---: |
| 已关闭 | 1 |
| 待付款 | 12 |
| 待发货 | 29 |
| 待收货 | 38 |
| 已完成 | 27 |

29＋38＋27＝94笔在状态上符合普通订单销售统计条件，但没有一笔明确记录CNY。`orders.analytics.sales_eligible_orders()`要求`currency='CNY'`，因此94笔均被排除，汇总为销售额0、已付订单数0、平均金额0。完成率依据订单状态单独统计，所以仍为27／107＝25.2%。

真实`GET /v1/supplier/analytics?period=year`的响应与上述数据库推导完全一致，并非浏览器缓存或请求失败。`paid_at`和非空支付流水均为0；状态只是原存储记录，不能作为真实渠道付款或币种证明。

该行为沿用[金额规格](../../architecture/currency.md)：历史缺币种记录不推断为人民币或美元，不进入跨币种财务比较。该NULL状态已在[0007历史迁移启用](../2026-11-02-priority-activation/verification.md)中记录，早于本次0008。0008只新增风险表，没有修改历史币种。

## 展示缺口与处理边界

当前卡片仅标注“已付销售额／已付订单数”，没有说明“仅明确CNY”和94笔历史记录被排除，容易把统计资格缺失理解为业务数据丢失。建议补充“94笔历史订单币种未记录，暂未计入人民币销售统计”，并区分状态计数与人民币财务计数。

本次没有以填数消除0，也没有批量补币种。历史修复需要订单、原交易配置、报价或支付记录等可信依据，并独立核验金额与币种；无法确认时继续保留未知状态。
