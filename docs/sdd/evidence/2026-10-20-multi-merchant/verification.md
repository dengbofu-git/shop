# 多商家模拟数据与实际接口验证

日期：2026-10-20。用户要求生成“模拟1、模拟2”、模拟商品、订单和配置，验证当前多商家模式；后续明确普通订单应按店独立。

## 结论

75 项定向检查，70 项通过、5 项业务断言失败。商品、库存、商家订单读取、销售额、结算及店铺配置的归属隔离通过；当前购物车结算缺少按商家拆单，并暴露共享订单发货／删除问题。试单、预售的发货状态也未接入现有商家发货接口。不能据此宣称完整多商家交易闭环已通过。

本轮创建数据并验证现有实现，没有修改上述业务代码或修复这些问题，没有新增／执行 Migration、重启服务、提交、推送或部署。

## 验证方法与通过范围

实际服务 `http://127.0.0.1:8000` 使用新账号的真实登录及 Bearer Token。登录／GET 请求走真实 HTTP；写入探针使用同一源码的 Django 路由、视图和真实认证装饰器，在业务 MySQL 事务内执行后强制回滚，只触及本批模拟记录，不绕过权限判断。

实际执行入口为 `python -X utf8 manage.py shell -c "exec(open('.scratch/multi-merchant-20261020/verify.py', encoding='utf-8').read())"`。该脚本为本机过程文件，不作为可移植工具交付。每项检查的名称、通过状态和必要观测值见 [verification.json](verification.json)，源版本与文件指纹见 [context.json](context.json)。最终完整性复核见 [postflight.json](postflight.json)。

通过范围：

- 两个商家登录均进入商家工作台，买家进入买家工作台；商家访问平台运营数据／用户／Agent 配置被拒绝。
- 商家只能读取本人 8 个 SKU、本人库存、本人 13 笔订单及 2 条结算；订单金额、数量均只计算本店明细。两家模拟销售额分别与独立计算的 641.00／840.00 一致，剔除未付、仅定金、已退货和取消状态。
- 越权修改／删除其他店商品、以别店 SPU 创建 SKU、修改／删除别店库存、发货／删除别店单商家订单均被拒绝。部分旧 API 的 HTTP 为 200，实际业务码为 403／404，验证同时读取业务码。
- 店铺配置从身份确定归属，不接受查询参数冒充商家；跨店推荐商品、跨店素材 URL 和过期 revision 被拒绝。草稿保存不改变公开快照，发布／下线生命周期通过，随后回滚。
- 两店公开页各 6 个可售商品，已发布推荐过滤售罄／下架项；店内搜索和排序不跨店；平台同时展示两家店商品且商家 ID、店铺链接准确。匿名／买家不能管理店铺或读取商家商品。
- 12 个可售商品的茶类回退图接口均返回图片；专用买家能看到全部 26 笔模拟订单，其他身份不能通过路径冒充其读取订单。
- 本店标准订单发货仅扣本店库存；全部写入探针回滚。最终逐行指纹核对涉及表中原有 1590 条记录未改变，本批创建记录完整，库存数量与出入库日志平衡，所有保留订单均只有一个商家。

## 失败项与复现

### F1：购物车结算没有按商家拆单（高）

当前 `orders/views.py` 的 `OrdersView.post`，`settlement_type='0'` 分支先收集所有选中 SKU，计算总额，创建一个 OrderInfo，再把全部明细关联进去，没有商家分组。这是买家从两家店选中商品后可能产生跨店订单的原因；单品立即购买不会产生这种组合。

验证：使用专用买家与模拟地址，提交两个分别属于模拟1／模拟2的 SKU；购物车读取和支付 URL 生成使用本机替代对象，不读写真实 Redis 购物车、不连接支付网关。现有路由返回 200，但只生成 1 个订单头，其明细属于 2 个商家。预期是每商家独立订单；事务结束后该订单已回滚。

### F2：共享订单不能由两个商家独立发货（高）

`supplier/views.py:SupplierOrderShipView.post` 只扣本店明细库存，却将共享 `OrderInfo.status` 从 2 改为 3。临时构造两店各一条明细的待发货订单后，模拟1发货返回 200、本店库存 -1；模拟2再发货返回 400，库存变化 0。所有操作回滚。

如果未来严格保证订单按商家拆分，这个共享头场景应在创建边界被禁止；在此前仍不能假定历史混合单可以正常发货。

### F3：商家删除共享订单会删除别店明细（高）

`supplier/views.py:SupplierOrderDeleteView.post` 确认订单含本人商品后，对整个 OrderInfo 执行 delete。临时混合待付款订单由模拟1删除返回 200，模拟2的明细由 1 条变成 0 条，说明发生级联删除。事务已回滚，不保留破坏结果。

### F4／F5：试单与预售待发货状态不被支持（中）

现有发货接口只接受基础表 `order.status == 2`，不根据 TrialOrder／PreSaleOrder 子表状态判断。模拟1的 `MM20261020-M1-T1` 为试单待发货、`MM20261020-M1-P2` 为全款预售待发货，两者基础 status 均为空，调用发货返回 400。两个状态适配分别记为一个失败断言。

## 限制与后续方向

本轮没有全站回归、真实浏览器界面验收、模型调用、真实支付／退款／资金结算或并发压测。销售、付款和结算状态为演示夹具，不能作为支付已到账凭据。仓库模型本身为共享资源，本轮只验证 SKU 库存的商家过滤，不宣称已具备独立租户仓库模型。

订单创建应先明确按商家分单，以及多订单支付／回调、失败原子性和库存处理，再修复实际交易实现；在此之前不能把仅调整演示数据视为已修复结算拆单。上述问题未在本轮静默修改，SDD 能力阶段未提升。
