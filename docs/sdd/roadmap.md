## 目标与优先级

2026-10-18项目聊天增量已按[统一对账](reconciliation-2026-10-18.md)纳入8域25能力34功能15实现模块，替代旧数量作为当前盘点。已实现的历史咨询／公开详情／商家入口不自动提升其他能力阶段。下一步优先补历史分页、停用账号差异、重放脱敏和推荐指代／检索质量的定向验收；MCP商品搜索及商家经营能力保持独立设计候选。旧阶段计划和责任审批要求继续保留，不把本次文档同步当作BUILD_READY或发布批准。

目标是让一个业务变化可以从页面入口定位到唯一规则归属，并追踪到需求、契约、测试和当前版本的验收证据。优先处理跨用户数据范围、交易状态和 AI 事实边界，逐步覆盖现有功能。

| 优先级 | 能力 | 原因 | 本轮处理 |
| --- | --- | --- | --- |
| P0 | CAP-IAM-003、CAP-TRD-003、CAP-FUL-002 | 对象级权限、支付回调和物流数据范围影响交易可信度 | 登记差异，列入首批规格评审；不在本轮修复 |
| P1 | CAP-AI-003 | 链路较完整，能验证权限、跨域只读契约、会话和证据管理 | 唯一活动试点，形成发现与验收草案 |
| P1 | CAP-TRD-001／002、CAP-FUL-001、CAP-MER-001 | 下单到发货跨越订单、库存和商家，需明确一致性 | 在试点方法稳定后做交易闭环 |
| P2 | CAP-AI-001／002／004、CAP-KNOW-001／002 | 近期已有改动较多，需固化推荐、RAG、模型配置的行为边界 | 下一批 AI 业务切片 |
| P2 | CAP-CAT-001／002、CAP-IAM-001／002、CAP-PLAT-001／002／003 | 为业务切片提供目录、账号、前端和运行支撑 | 按真实消费者补契约与验证 |
| P3 | CAP-MER-002／003、CAP-CAT-003 | 指标和结算规则仍需业务输入 | 保持候选；不宣称已有真实资金结算能力 |

`CAP-AI-003` 的规格发现可以与 P0 问题梳理同时进行；若其目标验收环境依赖受影响交易链路，相关 P0 缺口必须在发布前解决。试点只验证查询读取到的状态，不替交易域证明支付或状态来源正确。

## S0：建立可追踪现状

交付：本目录规划、来源登记、初步能力地图、功能盘点、开放问题。

完成条件：每条已登记功能只有一个主规则归属；明确采样范围；存量代码、演示和历史证据分开；未指定的负责人和未确认规则明确列出。本轮完成文档准备，**没有完成全量功能确认**。

下一步逐个核查买家、商家、运营入口的真实导航和 API 调用。补齐加载、空、失败、越权、重复操作状态及页面互跳上下文。全量核查完成后再将模块从 `REGISTERED` 提升为 `MAPPED`。

完成条件：结构和交互得到当前规格版本的确认，达到 `PROTOTYPE_VALIDATED`。纯后端增量若无需原型，用有理由的适用性决定处理，不能伪造原型阶段证据。

## S4：差异实现与分层验收

先列“符合／偏离／未覆盖”矩阵，再按已批准规格做最小实现增量。已符合的存量代码保留；不为 SDD 改造而重写整站。

| 验证层次 | 交付证据 | 能证明什么 |
| --- | --- | --- |
| 静态检查 | YAML、路径、ID、映射、Diff 检查 | 规划或契约结构自洽 |
| 隔离自动化 | 当前规格 AC 到测试结果映射 | 被覆盖逻辑的预期行为 |
| MySQL／PostgreSQL／Redis 集成 | 路由、迁移、并发、故障及数据范围结果 | 真实组件交互 |
| 页面／真实模型验收 | 合成账号场景、脱敏输入输出、配置与耗时 | 当前目标环境的端到端行为和模型质量 |

现有隔离回归命令可作为后续验证起点：

```powershell
python manage.py test support_ai.tests support_ai.test_planning support_ai.test_task_tools support_ai.test_telemetry support_ai.test_grouped_recommendations support_ai.test_mixed_tea ai_storage.tests --settings=support_ai.test_settings --noinput
```

该命令使用SQLite／LocMem，现已覆盖7个登记测试模块。本次对账通过专用脚本额外阻断网络并使用合成凭据，101项中98通过、3项真实PostgreSQL测试跳过；最初4模块的61/64与64/64分别作为历史快照保留，不混算。它不能验证真实pgvector、跨库事务、MySQL锁语义或外部模型质量。真实模型评测单独登记数据范围、模型／配置、样例数、成功标准和调用授权，不沿用历史调用授权。

达到 `VERIFIED` 后，再分别准备部署审批、目标环境部署证据和发布记录。不能根据历史报告的测试数量直接提升状态。

## S5：扩展交易闭环及后续能力

1. 先确认支付回调信任边界与订单状态机，定义金额／币种、重复通知、乱序和回滚结果。
2. 再确认库存权威字段、预留／释放／扣减时点、重复发货与并发下单，打通买家下单 → 商家发货 → 买家收货。
3. 补齐商品推荐、知识问答、偏好、检索和 Agent 运营的独立规格，复用已验证的权限及证据机制。
4. 对结算和经营指标分别做业务发现；只有真实外部系统、规则和责任确认后才规划正式集成。

每批完成后回顾：当前切片未知是否减少、AC 是否可执行、重复规则是否减少、真实验收是否可复现。文档数量和自动化测试总数不作为成功指标。
