# tea_saas SDD 工作约定（规划草案）

本约定参考 store-ai-tp 的渐进式 SDD 方法，仅用于本项目。它不引入来源项目的人员、Git 交付制度或自动检查命令。

## 规则归属和编号

- `MOD-*`：业务模块；Django App 与业务模块可以多对多。
- `CAP-*`：可以独立评审、实施和验收的能力切片，是阶段推进单元。
- `FEAT-*`：来源功能；一项只有一个 `primaryCapability`，其他参与者使用 `relatedCapabilities`。
- `JOURNEY-*`：跨页面／角色的业务旅程；由参与能力共同完成，不复制业务规则。
- `REQ-*／RULE-*／AC-*／TEST-*`：需求、业务规则、验收和测试。

追踪链：`FEAT → CAP → REQ／RULE → AC → CONTRACT／TASK → TEST → EVIDENCE`。当前试点的 AC 直接引用需求／规则，测试计划引用 AC；正式设计阶段再补契约追踪。

产品角色不是审批人；业务规则归属不是代码目录所有权。未明确的人员填写 `null`，不能自动填入来源项目的 Owner 或假定当前操作者已批准。

## 两种状态

模块使用 `REGISTERED → MAPPED`：前者表示边界登记，后者要求约定范围内来源功能已完整核查并唯一映射、模块说明和关键跨域关系明确。当前都是 `REGISTERED`。

候选能力使用 `candidate`，无正式能力目录。选中后进入活动生命周期：

```text
DISCOVERY → SPEC_REVIEW → PROTOTYPE_READY → PROTOTYPE_VALIDATED
          → DESIGN_READY → BUILD_READY → IMPLEMENTING
          → VERIFIED → RELEASE_READY → RELEASED
```

“已有实现”“已有页面”“历史报告通过”是不同观察维度，不替代上述状态。

| 目标状态 | 必须具备的内容／证据 |
| --- | --- |
| SPEC_REVIEW | 目标、范围、角色、主异常流程、规则、可观察 AC，影响业务含义的未知已解决，可进入评审 |
| PROTOTYPE_READY | 当前版本业务内容已确认，页面／操作／状态／敏感展示边界明确，负责人明确 |
| PROTOTYPE_VALIDATED | 当前版本体验评审记录及覆盖范围；正式原型需可追踪 manifest |
| DESIGN_READY | 业务与体验结论、技术设计、必要 API／数据／集成契约已确认 |
| BUILD_READY | 测试范围、依赖可用性、幂等与并发、兼容／迁移／回滚明确，无该阶段阻塞，准入记录有效 |
| IMPLEMENTING | 已获当前切片的实施授权，记录实现差异与代码范围 |
| VERIFIED | 当前规格版本、实现版本和目标测试环境匹配的通过证据 |
| RELEASE_READY | 验证通过、目标环境部署记录和发布批准；部署与验证独立记录 |
| RELEASED | 实际发布与上线验证记录，包含回滚依据 |

按风险确定适用文档；例如纯后端切片可说明原型不适用的依据及评审人，不能自动视为已经验证原型。当前试点涉及买家交互，需评审现有页面。

## 存量项目的增量方式

1. 区分来源说明、代码观察、建议规则与未决问题。
2. 从功能／页面定位唯一主能力，核对其他参与域和数据所有者。
3. 建立当前切片草案，明确所有假设；业务负责人确认后才把建议变成有效规则。
4. 对照存量代码列出符合、偏离、缺失；代码存在不迫使产品接受旧行为。
5. 补当前阶段所需设计和验证，不生成所有未来能力的空文件。
6. 实现与验证后，将新的业务结论回写规格，将运行结果存入独立证据。

原型和技术 Spike 可以提前探索，须明确非正式，使用合成数据，不能据此提升生产准入状态。

## 变更分流

| 类型 | 最小材料 | 验证选择 |
| --- | --- | --- |
| 文案／样式或符合既定规则的实现修复 | 变更说明、所依据规格／缺陷、预期结果 | 检查受影响文件／页面和直接回归 |
| 新增／改变业务规则、权限、状态、交互、API 或数据语义 | 受影响 CAP 的需求、规则、AC 和版本增量 | 当前切片及直接依赖的回归 |
| 支付、库存、跨用户数据、认证、跨库写入、外部集成 | 上述材料，加并发／幂等、失败、迁移与回滚设计 | 真实组件定向验证与目标环境验收 |

不因单纯改文档运行无关全量业务回归；不因测试是隔离环境就省略高风险变更的真实组件验收。持续维护不要求全仓一次性补齐 SDD。

## 依赖与跨端边界

依赖至少说明目标、类型及用途：`data-owner`（事实拥有者）、`platform-runtime`（运行支撑）、`optional-runtime`（失败可降级）、`delivery-blocking`（未交付则不能完成本切片）。只用最后一种决定交付拓扑；数据调用图不必无环。

`versions/modules.json.dependencies` 用于版本影响传播，与业务实施顺序不同；不能直接把它转成 SDD 阻塞图。尤其 `support_ai ↔ ai_storage` 的登记互依不应变成两个能力互相等待准入。

买家、商家、运营操作分别记录端级入口，订单状态等业务规则只由主能力定义；商家页面和 AI 查询可以引用订单事实，不重新定义订单状态机。

## 文档权威和证据

- `catalog.yaml`：模块和候选能力权威；活动阶段与其 manifest 保持一致。
- 活动 `capability.yaml`：规格版本、当前阶段、依赖、文件、问题和批准入口。
- `requirements.md`、`acceptance.yaml`：当前版本业务定义与验收草案／确认结果。
- `product/open-questions.yaml`：全局未决问题，只阻塞受影响能力及相应目标阶段。
- 一个全局问题可按能力部分解决：`partially-resolved` 须保留明确的 `resolutions[].capabilityId` 和剩余范围；本切片解决不自动解除其他能力的阻塞。
- `versions/modules.json`、`versions/changelogs/`：继续维护实现模块版本；`specVersion` 不替代模块版本、Migration 编号或配置 revision。
- 既有 `docs/` 说明继续保留；选定能力后逐条标明对应关系，产生冲突时登记差异，不能悄悄覆盖旧说明或保留两套互相矛盾的有效规则。

后续证据存放 `docs/sdd/evidence/<run-id>/`，按实际执行创建。至少记录：类型（verification／deployment／release）、CAP、规格版本、代码提交和工作区补丁／哈希、环境、数据库／模型配置版本（脱敏）、时间、命令、退出码、覆盖 AC、结论、限制、原始日志引用和评审人。

脏工作区不能只用 HEAD 表示被测代码；历史报告仅作输入。新增 YAML、ID 或链接校验通过只说明静态自洽，不证明业务验收通过。

本轮没有自动阶段检查器，以上准入由人工评审执行。待一个完整切片跑通、稳定字段确立后，再决定是否建设校验工具；不得提供不存在的 `check-sdd-readiness` 命令作为已生效门禁。
