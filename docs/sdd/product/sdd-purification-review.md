## 范围、依据与结论

目标仓库基线：`0d53d1423cbeb349730ff9462e5798fb5f58cb59`，分支 `codex/core-unified-runtime`，开始时工作区干净。审查前现行 SDD 有 70 个 Markdown／YAML 文件（排除 evidence）；扫描其结构、文本、链接与映射，重点核对身份、商品、交易、支付、库存、物流、商家经营和 Agent 源码。清单实际为 **8 个业务域、27 个能力、36 项功能、15 个实现模块**。这不是每个接口及分支的运行验收。

来源项目仅只读对照 `E:\实习\store-ai-tp` 的 SDD 入口、阶段策略及相关目录结构。其对象是门店、指导员、管理端的培训业务，有能力阶段、原型流程、团队责任和独立治理工具。目标项目则已有 Django 商城业务与 AI 客服，不适合整体继承该流程。

**没有发现足以把整个业务域认定为 Store 培训业务误植的证据。** 来源角色、课程／陪练业务、GitLab、Flyway 和 Owner Registry 没有作为目标 SDD 的有效业务规则引入。当前干扰主要是阶段残留、旧实现观察、重复规则及超出现有能力的产品叙述。SaaS、跨境、试单／预售在本项目已有定位或代码，不能仅凭未完成就归因为来源噪音。

## 仍需收敛的文档组织

1. Agent、总价推荐及部分 UI 规格含多个版本的追加段，存在“本轮”指向不明。后续按业务讨论结论合并当前规则；旧测试数字留在原 evidence，不以一次批量改写掩盖真实演进。
2. 27 个能力仅 2 个有独立 capability.yaml，其余多以清单、领域正文和代码映射表达。形式差异不等于不适用，也不要求补建 27 套模板；讲解链路时补齐真正缺少的需求／AC／契约。
3. MOD 是业务归属，不是微服务边界；FUL、KNOW 等没有同名规格目录，不据此新建 App。15 个实现模块和 8 个业务域不要求一一对应。
4. 不撤销已有 R01—R11、MCP 或人民币决定；规则不合场景的主张须指出具体用户行为、输入输出和代价，再由本次讨论形成新决定。
