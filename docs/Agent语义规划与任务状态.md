# Agent 语义规划与任务状态

实现版本：support_ai 0.23.1。预算口径新增受限上下文语义解释，保留规则快路及原金额来源；历史记录见 [回归修复证据](sdd/evidence/2026-10-19-regression-repair/verification.md)，本轮见[语义范围证据](sdd/evidence/2026-10-26-budget-scope-semantics/verification.md)。历史记录不代表本次增量已通过回归，不将合成测试视为生产流量准确率。

## 一轮如何处理

`登录及会话校验 → 脱敏 → 规则快路或一次语义规划 → 后端生成任务计划 → 固定工具执行 → 回复 → 原子保存轮次和状态`

当前字段缺少或引用错误时，允许再做最多一次PurchaseEvidenceRepair（extraction阶段），只返回失败字段的证据；不能改条件值、任务或放宽来源。unknown口径无需肯定证据；未证明口径时保存金额、具体追问单件或整套。新建单一推荐的明确单金额遗漏由保守原文检查补全，复杂遗漏澄清；普通预算不伪造cap模式证据。

这里的“一次”指语义规划调用。知识检索、知识回答、混合任务组合和安全检查仍可能调用模型，不代表整轮对话最多调用一次模型。

预算口径pending时，规则未命中的纯短答可先进行一次BudgetScopeDecision，仅判断单件／整套／不确定，不生成其他条件；不是纯范围回答时继续完整SemanticPlan，因此该类轮次可能有两个受预算控制的判断。scope阶段默认关闭thinking、最多192输出Token，与其他模型调用共享整轮预算，不能以“一次规划”名义漏记调用。

解释结果由程序绑定本轮原话及当前待补充轮次，保存context_turn_id并在未来历史读取时建立应用来源记录；后续口径校验不再要求固定同义词，但金额、币种、分类等继续逐项验证。模型不能生成内部引用字段。无原问题、无保存解释或来源过窗口时不能沿用。模型范围结果不确定只复问口径；格式／服务故障仍为技术失败。

HTTP 买家入口和终端预览共用 workflow。HTTP 登录要求保持；只有需要模型的请求才检查模型密钥、创建模型并读取长期偏好。终端预览启动时仍读取运行配置供状态展示，但模型客户端校验延迟到需要模型的请求。

## 先确定本轮在做什么

| turn_action | 含义 | 示例 |
| --- | --- | --- |
| new_request | 建立新任务，不继承旧任务的预算等条件 | 推荐绿茶 |
| supplement | 补足当前任务缺失的内容 | 前一轮缺币种，本轮说“美元” |
| modify | 修改当前任务已有条件 | 改成绿茶、单价上限改为30美元 |
| follow_up | 追问已有结果，不重新执行商品筛选 | 第二款有什么特点、为什么推荐这些 |
| cancel | 结束当前任务并清空状态 | 取消当前任务 |
| clarify | 无法可靠确定本轮要求 | 无明确对象且历史也不能唯一定位 |

只有存在当前任务，才允许 supplement／modify；补充任务类型不能突然变成其他工具。问候和功能帮助回复保留当前任务快照。明确的新推荐重新建立筛选条件；“介绍绿茶→推荐茶叶”仍可沿用近期用户明确提到的单一茶类，继承内容须有历史用户原话证据，多个主题进入语义规划。

## 规则快路

- 精确匹配的问候：你好、您好、hello等。
- 精确匹配的系统功能介绍：介绍系统功能、你能做什么等。
- 明确的基础茶类推荐：推荐绿茶、推荐一款红茶、推荐“白茶”等。
- 引号中的明确名称：推荐“龙井”茶。基础茶类按分类筛选，其他引号名称按商品名称关键词筛选，不自动猜测商品属性。
- 无未覆盖分句、复杂约束或未解决指代的既有显式任务可继续使用固定规则。
- “按照六种基本茶类各推荐一款，并给出理由”等精确、无额外条件的分组请求直接使用程序负责的茶类范围，不生成六个用户硬条件；预算、排除、认证等附加语句不进入该快路。
- 明确的本人偏好推荐请求读取服务端已保存软偏好；没有偏好时询问，不把偏好写成购买硬条件。复杂表述仍进入语义规划，不引用历史时独立问句必须保留本轮原文。

问候、功能说明和取消任务的固定回复不调用语义规划、组合和安全检查模型；简单单任务推荐直接调用受控商品查询。预算、品牌、排除、修改、缺项补充和复杂指代交给统一语义规划，避免关键词规则抢先丢掉条件。

### 问候与功能介绍的入口快路（0.15.0）

HTTP 顺序为：登录及输入校验 → 请求幂等／会话归属／revision校验 → 读取短期上下文 → 程序整句匹配 → 复用workflow生成固定响应 → 原子保存轮次。命中时跳过模型密钥校验、模型配置加载、模型创建、PostgreSQL长期偏好及知识检索、商品和订单查询；仍依赖登录及会话所在的业务数据库。未命中进入原有处理流程。

程序先做Unicode NFKC和英文大小写归一化，去掉首尾常用标点与空白，合并连续空白，再进行完整句子匹配。英文词内不删除空格，不删除业务词语，不使用子串命中。规则集中在 `support_ai/semantic_planning.py::fixed_reply`，固定文本为其中的 `GREETING`／`CAPABILITIES`。

| 输入示例 | 处理 |
| --- | --- |
| 你好、您好、哈喽、早安、hello、HI！、Ｈｅｌｌｏ | 固定欢迎语 |
| 有什么功能、有哪些功能、你能帮我做什么、请介绍一下系统功能、HELP、what can you do? | 固定功能介绍 |
| 你好，推荐红茶 | 原有业务处理流程 |
| 不要介绍功能，请查询我的订单 | 原有业务处理流程 |

欢迎语：“您好！我可以介绍茶叶知识、按条件推荐商品、查询商品详情，以及查看您本人的订单状态。”

功能介绍：“我可以帮您：介绍茶叶知识；按茶类、品牌和预算挑选商品；解释推荐理由；查询商品详情和本人订单状态。您可以说‘推荐绿茶’或‘介绍红茶和绿茶的区别’。”（实际文本使用中文双引号。）

固定响应继续使用 `greeting`／`system_help`、`greet_user`／`describe_capabilities`、`intent_source=rules` 与 `success` 任务状态；不生成商品卡片或知识引用，`memory_used=false`，保留已有任务快照。HTTP 保存后的请求可幂等重放，revision仍递增；问候不取消待补充的推荐任务。终端预览同样在长期偏好、订单上下文和模型调用前匹配，日志记录零模型调用、空检索记录。

## 统一模型输出什么

`SemanticPlan` 禁止未知字段，任务最多5项，包含：

- action：本轮动作。
- requests：有限意图、逐字取自本轮的quote和可选推荐数量。
- standalone_question：补全后的问题；改写必须引用历史source_turn_ids。
- source_turn_ids：只能使用本会话上下文已有轮次。
- result_reference：可选历史商品轮次、从1开始的列表位置，不能传SKU ID。
- purchase：购买条件、缺项及原文证据。补充／修改时只提取变化，程序合并已有条件。
- clear_fields：明确取消的条件路径；后端同时核对本轮是否提及取消对应范围。
- needs_clarification／clarification_question：对象不能唯一确定时询问。

工具名、执行步骤ID、依赖关系、SQL、身份和订单访问范围均由后端决定。商品引用校验后仍读取当前数据库，历史价格库存不能当作本轮事实。

## 待补充内容如何保存

状态保存在已有 `SupportTurn.response.dialogue_state` JSON 中，与回答使用同一事务及revision提交，无新增表。客户端不能提交或覆盖状态，只能提交既有message／conversation_id／request_id／expected_revision字段。

以下仅展示核心字段，实际还包含数量、分组方式、条件证据等：

```json
{
  "version": "1.0",
  "status": "pending",
  "task": "recommendation",
  "request": "推荐两款红茶，每盒不超过50",
  "limit": 2,
  "purchase": {
    "action": "CLARIFY",
    "required": {"categories": ["红茶"], "price_max": "50.00", "price_basis": "unit"},
    "missing_fields": ["currency"],
    "evidence": []
  },
  "missing_fields": ["currency"]
}
```

示例省略了证据内容；实际非空条件必须携带经校验的evidence。原轮CURRENT证据在读取时绑定真实turn_id并转换为CONTEXT，不根据助手回答重造条件。

下一轮“美元”应产生supplement及USD的新证据，程序保留红茶、50、unit和数量2，重新校验缺项，然后执行商品查询。若说“改成绿茶”，只替换分类及其证据。说“取消预算限制”时，清除金额、币种和预算范围，再重新校验；说“推荐白茶”建立新筛选条件。最终行为仍取决于模型能否正确返回通过契约校验的规划。

快照状态为idle、pending、completed。取最新已提交快照，旧会话没有快照时视为idle，不扫描历史助手措辞恢复任务。当前主要购买条件有完整结构，非购买任务只保留待确认任务和缺失对象，依靠受约束的历史引用继续。

## 边界与失败处理

- 仍只读取本人所选会话最近24小时、最多6轮、6000字符；结构化状态计入预算，仅最新轮次携带快照，避免重复塞入多份状态。
- 快照超过3000序列化字符时，只保留“任务需要重新说明”的最小状态，不能无声丢弃价格、品牌等约束后继续宽泛筛选。
- 原始证据所在轮次被窗口裁剪、偏好来源失效、引用越界或契约不通过时，返回明确的重新说明请求，不继续使用未经确认的条件。
- 语义规划契约校验失败不重走旧的“先补全再提取”链路；保留原状态并要求重新说明。模型服务异常继续交给现有HTTP503／预览错误处理，不提交成功轮次。规划器没有额外语义修复重试，底层模型客户端原有网络重试策略保持。
- 已产生的购买条件在工具入口再次校验。旧的独立工具／评测调用仍保留原条件抽取兼容路径；正式图流程复杂请求使用统一规划结果。
- 长期软偏好的引文由共享契约在确认本人偏好 ID 与已保存值后规范化；语义规划与工具入口保持同一边界。无法确认来源或值时仍拒绝。
- 状态不保存新的长期画像，也不扩大知识ACL或订单权限；原有显式长期软偏好继续由服务端核对。

## 订单查询工具增量（0.17.0，2026-10-23）

HTTP和预览的顺序调整为：身份／会话与幂等检查 → 本地编号解析及脱敏（不查库）→ 规则或Agent语义规划 → 服务端生成after_sales任务 → execute_plan执行get_order_status → query_orders读取本人订单 → 固定回复 → 成功提交及绑定保存。其他意图不执行订单工具。长期偏好读取和模型配置仍沿用原依赖策略，不代表订单问题已完全摆脱这些服务依赖。

### 契约及可信上下文

- `order_contracts.py`仅定义纯契约与文字解析：OrderQuery由selector（latest／recent／selected／explicit及可选reference）和topic（order_status／payment_status／shipping_status）组成，附在对应IntentRequest及TaskStep中，不接受SQL、用户ID或真实订单号。输出使用OrderQueryResult／OrderQueryData／OrderSummary白名单契约，最多3笔。
- Python识别带订单号／订单编号／单号／order id等标签的6至64字符编号，以及订单问题中的10至24位纯数字候选；每个请求生成随机ORDER_REF引用，真实编号映射只在当前请求的OrderQueryContext中保留，不进入图状态、Prompt、响应或日志。无法识别的格式应重新以明确标签提供；不扫描数据库猜编号。
- 规则处理明确参数，复杂表达由统一语义规划器填写order_query；执行前再次按当前任务原话核对selector、topic和引用，不能丢掉多个编号、日期、商品等未支持约束后宽泛查询。取消、退款和退货不作为本工具可执行操作。
- OrderQueryContext由HTTP／预览注入本人身份、会话标识和私有引用；不能由模型或HTTP请求体构造。工具重新检查活跃买家与会话归属，所有订单查询均有本人过滤且排除buyer_hidden订单。

### 查询与输出

- 显式编号只精确查本人该笔；latest取最新一笔；recent最多3笔并保持匿名标签，不自动绑定其中一笔；selected须有24小时内有效绑定，否则澄清。近期多笔结果的后续精确查询当前需提供订单号，未新增选择卡片协议。
- SQL只投影编号（工具内部使用）、类型、标准／试单／预售状态及创建时间；不读取收件人、电话、地址、交易流水等字段。状态字典以orders模块为准；缺子记录和未知状态返回无法确认。付款／发货是对既有订单状态的解释，不是实际到账核验或实时物流轨迹。
- 单订单任务不调用组合或合规模型；混合任务保留程序生成的订单文字，其他任务仍按原组合／合规流程。`order_result`只含status、匿名orders及queried_at，真实订单号不随任务结果返回模型。
- 本人无记录返回no_match；无有效引用或条件超范围返回needs_clarification；数据库故障由执行器转为error，全部工具失败时HTTP503且不保存轮次。
- 明确编号在本人可见范围中不存在时，HTTP返回404／ORDER_NOT_QUERYABLE、不回退近期订单、不保存轮次，外人与不存在一致。该判断发生在意图及工具执行后；复杂／混合问题可能已经发生模型调用，不声称实现旧草案中的“模型前404”。
- 工具成功选中唯一订单后，只有整轮提交成功才保存绑定；提交时再经查询模块复核归属与可见性。新追问重新查询，同request_id重放保存结果及原查询时间，不宣称实时刷新。咨询被删后的迟到提交继续409。

### 兼容与检查边界

`current_order_context`仅保留为旧本地调用的适配器，委托同一工具，不保留第二份ORM查询实现；正式HTTP与预览不再调用它。旧工具工厂的order_context参数保留位置兼容但不再消费，不能凭传入字符串取得订单事实。历史评测和旧mock没有据此自动获得新订单工具上下文。

本次是同一Django进程中的职责隔离，未创建独立查询服务、数据库账号或网络隔离。未新增Migration，未新增或运行自动化测试、浏览器交互、真实模型或业务库订单查询；静态及配置检查不等于完成真实数据库／并发验收。


## 前置存储失败与恢复（0.17.2，2026-10-23）

失败轮次不会作为成功问答写入SupportTurn或推进revision，页面中的错误气泡也不作为后续模型历史。新问题生成新request_id；同一问题网络或5xx失败后重试保留原ID，保证可能已完成提交的请求能够幂等重放。前端4xx结果清除pending，409仍按既有流程重新读取会话，不把错误永久绑定到会话。

问候快路不读取长期偏好，其余请求仍按已确认策略依赖PostgreSQL记忆读取。因此“你好成功、换几个业务问题都失败”可能是共享前置服务持续异常，不能由表现直接推断为上一轮失败污染了对话。不得通过返回None或跳过偏好来掩盖依赖故障。

saved_preferences对已识别断链（SQLSTATE08类／服务重启类，或确定的连接关闭提示）且不在事务内的只读查询，关闭ai_storage旧连接后最多重读一次；不重跑Agent、整轮HTTP、事务或写操作。认证、权限、缺表／缺列错误不自动重试。失败返回503及MEMORY_STORAGE_UNAVAILABLE或MEMORY_STORAGE_CONFIGURATION_ERROR，retryable分别为true／false；其余前置数据库故障返回SUPPORT_STORAGE_UNAVAILABLE。响应不含凭据、原始数据库异常或SQL。配置故障需修复配置，服务持续不可用时新问题仍可能失败，重建咨询不能修复后端依赖。

页面在失败时替换上一轮的“咨询已保存”提示，说明本轮未收到成功回复；偏好服务错误单独提示恢复后继续本咨询，不宣称未知网络结果一定未提交。

本次只读诊断确认当时的新MySQL／PostgreSQL连接、记忆表及字段投影可用；未获得截图当时异常栈，根因不能确认为断链。检查未读取客户问答内容、未修改业务库、未调用真实模型；未新增或执行自动化测试、浏览器恢复回归或故障注入。当前运行服务曾使用--noreload，源码变化不等于该进程已加载修复。

## 全部订单与独立创建日期筛选（0.18.0，2026-10-23）

用户确认采用all表示全部匹配订单，时间范围独立于selector；本节替代0.17.0中“日期不支持、结果统一最多三笔”的限制。其他权限、失败策略、请求幂等及显式不可见订单404边界继续适用，CAP-AI-003仍为SPEC_REVIEW。

例如“查询2026年10月1日至10月23日的全部订单”，语义槽位为：

```json
{
  "selector": {"type": "all", "reference": null},
  "topic": "order_status",
  "filters": {"created_date": {"start": "2026-10-01", "end": "2026-10-23"}},
  "page": "first"
}
```

- `all`不限制总匹配数量；每次只读20笔，按创建时间、订单号倒序。按用户后续确认移除latest选择器，询问最近／最新订单统一recent最多3笔；仅explicit指定编号和selected既有绑定返回一笔。通用TaskStep.limit不决定订单页大小。all／recent不自动选择第一笔为后续单笔绑定。
