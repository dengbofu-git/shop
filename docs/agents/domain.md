# 领域术语与架构决定约定

处理涉及业务含义、领域命名或架构取舍的任务时，先读根目录 [CONTEXT.md](../../CONTEXT.md)，再按影响读取相关 CAP 与 [ADR](../adr/README.md)。普通文案、样式或机械修改不要求遍历所有领域文档。

- 任务名称、接口说明、测试描述使用现有领域用语；保留已有代码标识，不因文档用词统一批量重命名 App、模型或接口。
- 新概念先核对 [能力清单](../sdd/catalog.yaml)及相关需求。业务含义不明确时记录开放问题；不要从代码名称补造规则。
- `CONTEXT.md` 是术语和来源入口；业务规则归当前 SDD，代码模块版本归 `versions/modules.json`，实际运行结论归各次证据。
- 跨模块架构选择、有持续影响的技术取舍使用 ADR。局部修复、任务进度和单次验证不必单独建 ADR。
- 遇到与既有 ADR 或有效规格冲突的方案，明确引用冲突点和影响，先记录提议；未确认前不得静默覆盖原结论。
- 本地探索留在 `.scratch/`；需要共享的事实和决定及时回写正式文档。来源项目和历史报告只能作参考，不继承其人员、审批或部署状态。

查找 CAP、REQ、RULE、AC 等引用可使用[SDD 引用检索](sdd-refs.md)。该命令只查文本引用，不校验业务正确性或推进能力阶段。
