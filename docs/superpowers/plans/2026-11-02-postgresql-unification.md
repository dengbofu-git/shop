# PostgreSQL 单库迁移实施计划

目标：将业务 MySQL 与 AI PostgreSQL 收敛到一个 PostgreSQL 数据库、一个默认 ORM 事务连接，保留 Redis、媒体文件、MCP 和业务边界。记忆新功能不在范围内。

基线：eb39a3e，分支 codex/core-postgresql-unification。复用持久主工作目录；没有并行实施，不新增 Worktree。用户授权实施独立迁移任务，不推导 Git 提交、推送、合入或生产发布授权。

## 任务1：配置与事务路由

- 先添加配置、路由及同事务回滚的失败用例。
- `tea_saas/database.py` 提供 `database_config(environ)`：默认统一 PostgreSQL；显式 legacy 模式仅用于旧来源读取/恢复及已有分库测试。统一模式的 AI ORM、显式 using、事务使用 default；测试模式兼容隔离 SQLite 和已有分库 PG 测试。
- 新增集中 `ai_storage.database.alias()`，替换生产 AI 服务的固定 ai_storage 字面量；历史 Migration 不改。
- 验收：配置单测、AI 与用户记录同一事务回滚、单库全部迁移和真实 PG 测试。

## 任务2：真实 PostgreSQL 兼容与回归

- MySQL 专属并发测试扩展支持 PG，并证明这些用例实际执行；保留库存、支付、权限和幂等语义。
- 新增隔离统一 PG 测试设置/容器入口，CI 使用 pgvector PostgreSQL 与独立 Redis，不用 SQLite 代替最终数据库验证。
- 核对账号比较/导入去重、PG 行锁、异常事务、JSON、时区、原币种 NULL 和 Decimal。不暗中扩大业务变更。
- 主业务运行依赖逐步移除 MySQL；迁移读取驱动作为专用工具依赖保留。

## 任务3：迁移工具、备份与演练

- `tools/database_transfer.py` 提供只读来源盘点/导出、空目标导入与核验；保留主键和字段值，规范化时区、Decimal、JSON/向量用于内容摘要。
- 目标必须新建、显式登记且拒绝覆盖；来源只读；不复制旧 django_migrations 掩盖缺表。目标用未经修改的迁移建表，协调初始化种子数据、序列和 AI 派生搜索字段/触发器。
- 先合成夹具验证孤立引用/不完整归档/非空目标拒绝；再从真实来源备份演练迁移，原库不写入。
- 验收：备份可恢复、全部来源表归属明确、原业务字段/ID/金额一致、序列正确、两类来源完整进入新库。

## 任务4：切换与收口

- 在演练、完整回归与独立整体验证完成后，形成可审阅的切换收据。原 MySQL/PG 保留，不删除或回退历史库。
- 最终一致快照须暂停本项目写入进程，迁移后统一配置并重启 Web/MCP/知识 Worker/到期清理；新库开始接收写入后不能盲目切回旧库。
- 更新 SDD、ADR、模块版本/changelog、运行模板和备份恢复说明；记录源码/测试指纹及实际启用边界。
- 不自动提交、推送、合入、发布或删除其他项目数据库/容器。

## 重点审查

别名相同物理库仍独立事务；迁移跳过记录不证明表存在；初始化账户不得覆盖原密码；来源时区和 JSON/向量规范化；导入主键后的序列；旧缓存身份/订单预留时限；并发测试不得条件跳过。一次完整分支新上下文审查在收口前执行。
