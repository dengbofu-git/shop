# 买家合并付款与商家独立订单 Implementation Plan

> **For agentic workers:** Use superpowers:subagent-driven-development / superpowers:executing-plans；按仓库实际授权，不自动Git提交、业务库迁移或部署。

**Goal:** 买家对同一次结算的待付商家订单一次付款，保留独立金额、库存、发货、收货、评价及未来售后归属。

**Architecture:** 新增pays付款单、不可变订单金额分摊和统一渠道收据；渠道交易号绑定付款单，不能复制到多个现有唯一订单流水列。原买家锁协调支付、取消和到期，整次有效合并付款确认原子提交；旧订单号回调共享收据唯一性。

**Tech Stack:** Django5.2/Python3.13、PostgreSQL16、现有支付宝SDK及原生JS。

**Spec:** 用户确认“买家合并付款，商家独立订单、独立履约和售后”，随后明确选择“先实现合并付款，售后仍按子单保留边界；退款流程单独做”。替换[独立付款限制](../../sdd/modules/trade/merchant-order-isolation.md)，保留[库存预留](../../sdd/modules/trade/stock-reservations.md)及[金额](../../sdd/architecture/currency.md)保护。

## Design and Decisions

- 比较只改按钮、直接将三个交易号合并、增加独立支付域三种方式：前两种无法正确核验总额与退款归属，采用独立付款单和不可变分摊，商家订单不合并。
- PaymentOrder为不可变渠道付款尝试（pay_前缀唯一外部单号、买家、CheckoutRequest、CNY、总额、固定截止、状态／异常）；同一结算只能有一个待付尝试。模型可保留多次尝试历史，但本阶段不在未确认旧渠道已关闭时自动重开。
- PaymentAllocation记录付款单、商家订单、购买商家、商品金额、运费和应付金额快照；同付款单同订单唯一，商品金额加运费必须等于订单头total_amount；分摊amount取该订单头应付，父付款只求和订单头，运费不重复累加。未来退款可精确定位该分摊，不实现实际退款或分账。
- PaymentReceipt是支付宝流水唯一事实源，统一新付款单和旧订单号回调，记录完整到账金额和处理结果。历史已有非空订单流水仅登记为legacy_reference，不补造渠道验签／付款证据，不改旧列或未知币种。
- 首次付款汇总同一次CheckoutRequest内本人的、有效受管普通CNY待付订单，已关闭或已付款部分不重复收费；缺可信库存、币种、归属或有效截止时拒绝。首次付款前的取消可按剩余待付款汇总。
- 付款尝试生成后金额及分摊固定。相同集合重试复用，不续期；子单取消、其他路径付款或金额变化后，本地标记失效并拒绝再签发链接／自动新建其他总额尝试。旧签名链接无法仅靠本地状态撤回；渠道关单／查询确认和退款自动化不在本阶段，不能宣称已杜绝渠道重复扣款。
- 可信正常到账在一个事务中将全部有效分摊及子单确认付款、holds转paid，保留各自金额和paid_at；子单的旧unique payment_trade_no不写同一个合并流水。迟到或子单已变动的到账完整记录待人工核验／退款，不复活库存、不部分确认新付款；对仍未付的有效占用按payment_review原因关闭释放，不新增买家滥用处罚。已由其他渠道确认的子单不重复释放或覆盖原付款事实。
- 同一交易号同目标同金额通知幂等；相同流水不能归属另一付款单或旧订单。不同交易号的重复到账有独立收据、标记待核验，不重复消费库存。金额／签名／app／seller错误拒绝；GET返回不确认付款。
- 所有写路径先定位买家，按买家→关联付款单→升序商家订单→SKU／库存及hold协调；旧单确认、关闭和到期也纳入付款锁与失效处理。外部网络调用不在持锁事务中执行；本地SDK构造付款URL不等于真实扣款。
- 本阶段只沿用现有配置的支付宝收款方；PaymentAllocation不是商家真实到账凭证。独立售后仅保留商家订单与付款分摊归属，售后工单、退款审核／渠道退款、实际商家分账另行实现。

## User Flow and API

- 保留用户在“前端”chat最新要求：提交前不恢复技术说明，按钮仍为“提交订单”。提交后展示商家金额明细与一个“合并付款”入口，不再要求逐店付款。
- POST `/v1/pays/checkout-payment`，JSON `{checkout_id}`，仅有效本人买家；响应code/data，含payment_id、checkout_id、currency、total_amount、expires_at、status、payment_exception、orders和pay_url。客户端不提交金额或任意订单集合。
- 保留既有本人订单付款入口：带checkout的有效订单统一取得该组付款数据；旧NULL checkout单继续原单付款及原未知币种／库存核验限制。
- 创建订单返回payment_mode=combined及checkout_id；旧后端没有能力标识时安全引导查看订单，不伪造合并支付已启用。网页只显示买家需要的金额、状态与动作，禁止把锁、预留预算、内部流水等实现说明放回提交页。

## Global Constraints

- 不修改旧Migration、旧金额、币种、库存、商家归属或截止；新pays.0001在隔离真实PG验证，业务库备份／迁移／重启单独授权。
- 900秒固定截止、20SKU、3组准入、账号／店铺额度和采购车清理任务不变；付款不创建新的订单或新预留。
- 保留现有站内咨询、商家独立发货、收货和评价；不声称独立退款／商家自动分账已实现。
- 保留现有PG-only、统计说明和外部前端“提交订单”文案改动；所有文件先比对现场，仅改本次授权增量。

## Review Focus

- 并发重复通知、跨买家复用同流水、旧订单回调与新父单回调共享唯一收据。
- 付款对取消／到期的真实PG锁竞争，不能出现部分paid或库存复活。
- 链接发出后子单变化，旧链接迟到到账及另一笔实际到账，金额证据不丢失。
- 配置缺失、错误签名／金额／来源、旧未知币种、缺失hold及客户端篡改均不能推进付款。
- 合并成功后两商家独立发货，一家操作不改变另一家的状态或物流／评价归属。
