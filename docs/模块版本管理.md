# Dadashop 模块版本管理

本仓库采用同一 Git 仓库内的模块独立版本。模块清单和当前版本以 `versions/modules.json` 为准，历史说明保存在 `versions/changelogs/<模块>.md`。现有 Django App、路由和导入路径继续使用原目录。

## 模块边界

| 模块 ID | 职责 | 主要目录 |
|---|---|---|
| core | Django 配置、入口、共享工具、依赖清单、版本管理工具 | dadashop、manage.py、requirements.txt、tools、versions、通用文档 |
| users | 用户、认证、角色、权限、地址 | users |
| goods | 商品、分类、品牌、规格和商品媒体 | goods、media、goods_data.json |
| carts | 购物车 | carts |
| orders | 订单和报关业务 | orders |
| pays | 支付集成及支付公钥 | pays、app_key |
| news | 内容与资讯 | news |
| inventory | 仓库、库存及库存流水 | inventory |
| logistics | 物流、运单及轨迹 | logistics |
| supplier | 商家业务、结算及经营分析 | supplier |
| admin_panel | 平台运营管理 | admin_panel |
| support_ai | 智能客服、推荐、会话及 MySQL 会话迁移 | support_ai、客服商品推荐设计文档 |
| merchant_ai | 商家智能助手入口、能力状态和后续商家任务编排 | merchant_ai、商家智能助手设计文档 |
| ai_storage | PostgreSQL 长期偏好、知识库、向量及部署配置 | ai_storage、deploy/postgres、compose.ai-storage.yml、相关文档和环境示例 |
| web | 买家、商家和运营页面、前端脚本和样式、邮件模板 | client、templates |

路径归属由清单确定；更具体的路径优先于上级目录。新增文件应归到上述边界，新增模块需同时补清单和变更记录。`dependencies` 表示需要评估的代码或运行依赖，不是 pip 依赖约束，也不保证任意版本组合兼容。AI 存储的旧偏好搬迁命令依赖客服契约，客服又读取 AI 存储，因此二者需要联合评估。

下段的 `0.1.0` 描述保留初始化基线语境，不表示全部模块的当前版本。

当前代码作为每个模块的 `0.1.0` 初始基线，统一标记于同一提交；此编号不代表已经完成生产稳定性验证。今后按模块分别升级：

- patch：兼容的缺陷修复，例如 `0.1.0` → `0.1.1`。
- minor：兼容的新能力，例如 `0.1.1` → `0.2.0`。
- major：不兼容的接口、字段或业务规则变化，例如 `0.2.0` → `1.0.0`。

Git 标签采用 `<模块>/v<版本>`，例如 `support_ai/v0.1.0`。标签指向包含完整项目的 Git 提交；模块版本独立记录，但系统仍按完整提交部署。部署时记录提交 SHA 及该提交中的模块版本清单。

## 日常操作

在项目根目录运行，脚本仅使用 Python 标准库，无需启动数据库：

```powershell
python tools/module_versions.py list
python tools/module_versions.py check
# 查看尚未提交的修改归属
python tools/module_versions.py changed
# 查看相对指定发布基线的修改，并包括本地未提交修改
python tools/module_versions.py changed --base support_ai/v0.1.0
# 升级一个模块并写入变更记录
python tools/module_versions.py bump support_ai patch --note "修复客服会话读取错误"
```

修改模块代码时将代码、`versions/modules.json`、该模块变更记录一起提交。前后端同时变化应分别升级相关后端模块和 `web`；共享配置变化评估 `core`；数据库迁移随所属应用发布。单纯更新模块版本元数据无需升级 `core`。只有依赖兼容性评估实际导致代码变化或需要明确的联合发布时，才升级依赖模块。

```powershell
git add support_ai versions/modules.json versions/changelogs/support_ai.md
git commit -m "fix(support_ai): 修复客服会话读取错误"
# 先推开发分支并通过 PR 合入 main；不要直接推 main
git push -u origin codex/support_ai-session-fix
# PR 合入后，在开发分支同步最新 main，工作区须干净
git fetch --no-tags origin refs/heads/main:refs/remotes/origin/main
git merge --no-edit origin/main
python tools/module_versions.py tag support_ai
# 确认标签提交已进入 main，再单独推送版本标签
git push origin support_ai/v0.1.1
```

工具的 `bump` 不会提交；`tag` 只创建本地注释标签，不会推送。初次建立基线可用 `tag all`，后续通常只给本次发布的模块创建标签。发布标签视为不可变记录，修正发布应增加版本号，不能覆盖已有标签。

## 分支、迁移与回退

模块版本和开发分支分开管理。日常开发可使用 `codex/<模块>-<任务>` 分支，完成后合并到 `main`，再创建模块标签。无需为每个模块建立长期分支。

提交和推送门禁以 [Git 协作规范](Git协作规范.md) 为准；先安装本地 Hook，版本清单、模块代码和 changelog 精确提交，推送前同步最新主干并验证。

数据库迁移属于模块版本的一部分，但 Git 标签不会自动执行迁移。上线前查看迁移计划并备份数据库；回退代码不等于回退数据库。尤其客服会话使用 MySQL，长期偏好使用 PostgreSQL，部署需分别执行：

```powershell
python manage.py migrate support_ai --database default
python manage.py migrate ai_storage --database ai_storage
```

这两条命令只作为部署步骤记录，本次版本管理初始化不会执行数据库迁移。
