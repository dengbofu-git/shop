## 失败原因与下一步

### 1. 原推荐列表被单商品解释结果覆盖（组 9）

实际对话：

> 用户：推荐三款白茶
> 用户：解释第二款的推荐理由
> 用户：再解释第三款的推荐理由
> Agent：这个位置在上一份推荐列表中没有可定位的商品，请说明列表中的有效位置。

第一轮原列表有 3 个 SKU。第二轮 `recommendation_references` 只保存筛选后的第二款；`context_from_turns` 又按这个子集重新编号。第三轮理由工具优先采用最新解释轮的单商品引用，原第三款因此无法定位。

建议优先修复：保存稳定的推荐列表 ID、完整有序 SKU 集合和原显示序号，另设当前关注 SKU；理由解释只改变关注对象。后续“第 N 款”默认基于完整列表，用户明确切换列表时才更新。涉及 `recommendation_explanations.py` 的引用筛选/返回和 `context.py` 的引用保存。

### 2. 范围、条件补充被当成独立任务（组 7、15）

`extract_requests` 将“不限茶类”和“指每包单价不超过20美元”归为未覆盖分句；规则要求为未覆盖分句补任务，模型没有给出新任务时还会补 clarification。最终计划同时包含 ask_clarification 和 recommend_products。

这两轮当前商品筛选正确，但 API 错误标记需要澄清，还增加组合及检查调用；最终文字隐藏了这个任务冲突。建议将重置范围、预算单位补全等识别为现有购买任务的修饰条件，保留完整本轮原话给条件抽取，不为已覆盖的约束分句强制生成澄清任务。

### 3. 分组理由追问重复命中详情规则（组 10）

“解释第二类商品的推荐理由”同时命中解释动词的商品详情规则及理由规则。当前理由消重对“第 N 款”做了处理，未完整覆盖“第 N 类商品”。前置指代解析、组合及合规使该轮发生 3 次模型调用，耗时 6.046 秒；单独理由追问通常约 1 秒。

建议理由意图在同一语义片段内优先，统一处理“第 N 款／第 N 类商品”，仅在用户额外明确要求价格、库存等独立详情时再生成详情任务。

### 回答内容复核

- 白茶理由真实使用当前分类、包装、净含量和模拟属性，并区分每份售价与每 100 克价格。尚未收集用户偏好时，不据此宣称个性化最优。
- 多数知识回答偏向分类和加工；“选购要点”的实用建议主要围绕分类、标签和工艺，尚不能据此评价选购咨询的全面性。
- 组 3 回答写“上述来源均未标注具体年份”，同时引用了 ISO 20715:2023，存在年份表述不一致。该项不在本轮预设结构断言内，作为额外内容问题保留。

本轮仅测试及分析，生产 Agent 源码哈希前后一致；上述三类边界问题尚未修复。

## 抽取契约专项

- 8 项纯本地契约探针全部通过：合法字段放行；数组索引、quantity/reasons/limit、非原话证据和外来历史 ID 被拒绝。
- 5 项独立本地故障注入全部通过：首错次对恢复、连续非法字段为系统错误、真实缺币种为业务澄清、连续伪造来源被拒、简单规则不调用模型。
- 故障注入没有外部模型调用，不能算作真实模型的纠错成功率。真实对话中 4 轮进入模型条件抽取，均只提取一次，没有自然触发字段纠错或契约错误。
- 故障注入结果以 `contract-recovery-v2.json` 为准；`contract-recovery.json` 保留初版记录。v2 更正了币种缺失用例的输入，使输入本身确实不包含币种；15 组真实对话及预设检查未改动。
